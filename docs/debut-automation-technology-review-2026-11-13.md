2026-11-13 한국시간 기준 · 검토·설계 문서 · 인건비 제외

**제안: 기존 Cloudflare Workers·D1 등록기를 유지하고, ‘검색 주소 찾기’와 ‘원문 읽기’를 분리한 수집기를 연결합니다. 기본은 Tavily Basic+허용된 공개 원문 조회입니다. X에만 있는 신인 공지까지 안정적으로 처리하려면 X 공식 API를 별도 선택해야 합니다. OpenAI는 검색 대안 또는 어려운 원문의 항목 추출 보조로 사용합니다.**

이번 작업은 공식 문서 조사·현재 코드 확인·기술 비교·문서 보완입니다. 계정 생성·검색 API 호출·실제 신인 조사·과금 설정·운영 DB 변경·코드 개발·배포를 하지 않았습니다. 아래 비용은 가정에 따른 계산이며 실제 청구액이나 발굴 성능 측정 결과가 아닙니다.

## 1. 현재 문제와 기존안에서 부족했던 부분

| 현재 상태 | 문제 | 보완할 기술 |
| --- | --- | --- |
| SOOP 공식 일정→CSV→공개 등록은 구현됨 | 공식 일정 밖 치지직 개인 신인은 출발 주소를 모를 수 있음 | 이름 없는 키워드 검색 연결 |

| 검색 시험 코드는 X 주소 위주 | 커뮤니티·일반 공식 공지가 결과에 있어도 처리하지 못함 | 출처별 원문 처리기와 지원 상태 관리 |
| X HTML 메타데이터를 직접 읽는 경로가 있음 | 접근 제한·본문 누락·비공식 자동 조회의 이용 조건 문제 | 상업 운영 적합성 재검토. X API 연결 또는 해당 경로 보류 |

| 문자열·정규식으로 행사 일시를 추출 | 이미지 공지·여러 멤버·다른 시간대·연기 글을 놓치기 쉬움 | 구조화 파서+항목별 근거+제한된 AI 보조 |
| CSV 원문 전체를 D1에 버전 저장 | 변경이 누적되면 묶음 크기 제한에 도달 | 회차별 묶음 저장·크기 경보·분할/보관 전환 계획 |

이 표는 현재 저장소 코드와 11월 13일 배포 기록을 기준으로 합니다. 이번에 운영 서버를 새로 조회한 결과는 아닙니다. 기존 실제 신규 사례 슈리리_는 SOOP 일정 발굴 사례이며 범용 검색 성공 사례가 아닙니다.

## 3. 추천하는 두 운영 수준

| 항목 | A. 비용 최소 기본안 | B. X 원문 확보 확장안 |
| --- | --- | --- |
| 공통 | Workers 예약, D1 대기열, 기존 CSV·등록기, SOOP 공식 일정 | A와 동일 |
| 웹 검색 | Tavily Basic 월 최대 280회 | Tavily 일부 검색을 X 검색으로 교체. 총 검색 요청 상한은 유지 |
| X 처리 | 발견 URL은 기록하되 허용된 원문 근거를 확보하지 못하면 보류 | X 공식 검색·게시물 조회로 공개 본문 확보 |
| 자동 등록 범위 | 공식 일정·읽을 수 있는 본인/공식 공지의 검증 완료 후보 | X 공개 공지 중 검증·사용 조건을 충족한 후보까지 확대 |
| 추가 외부 서비스 요금 | 무료 잔여량 안에서 검색료 0달러 목표 | X 월 5달러 이내의 사용량 제한 제안. 실제 결제는 별도 결정 사항 |
| 핵심 한계 | X에만 공지한 치지직 신인은 보류가 많을 수 있음 | 비용 외에 삭제·정정 반영과 계정/채널 연결 기준을 구현해야 함 |

**추천은 A를 구현 가능한 기본 구조로 만들고, B를 독립 모듈로 연결할 수 있게 설계하는 것입니다.** 목표가 ‘X 단독 공지 신인까지 처리’라면 B가 실질적인 기능 확장입니다. 비용을 쓰지 않는 A를 그 목표까지 완성된 자동화라고 보고하면 안 됩니다. OpenAI 웹 검색으로 바꾸어도 원문 접근·권리 문제는 그대로 남습니다.

## 4. 각 API를 실제로 어떻게 쓰는가

### 4-1. Tavily: 새 공지 주소를 찾기

- 인증: 서버 비밀값으로 보관한 키를 `Authorization: Bearer`에 넣습니다. 브라우저에 키를 보내지 않습니다.
- 호출: `POST https://api.tavily.com/search`.
- 설정: `search_depth=basic`, `max_results=10`, `topic=general`, `include_answer=false`, `include_raw_content=false`, `include_images=false`, `auto_parameters=false`.
- 입력: `치지직 버튜버 데뷔 2026 11월`, 치지직 공개 커뮤니티 검색, SOOP 공지 검색, 다음 날짜 묶음. 인물 이름 없이 시작합니다.
- 출력: `results[].url/title/content/score`를 내부 검색 결과 형식으로 변환합니다. `content`는 검색 미리보기이고 확정 사실이 아닙니다.
- 날짜 주의: 검색 API의 `start_date/end_date`는 **문서 게시일**, 우리가 찾는 날짜는 **방송 데뷔일**입니다. 미래 데뷔일을 게시일 필터에 넣으면 공지를 놓칩니다. 검색어에는 행사 기간을 넣고, 본문에서 행사일을 별도 추출합니다.
- 처리: 추적 문자 제거→URL 중복 검사→출처 분류→원문 대기열. 새 주소 수를 새 버튜버 수로 세지 않습니다.

공식 안내는 결과 메타데이터·출처 URL의 보관을 허용하되 원문 권리는 별도라고 설명합니다. [API 설정·날짜 기준](https://docs.tavily.com/documentation/api-reference/endpoint/search), [보관 범위](https://help.tavily.com/articles/1612400809-storing-caching-retaining-output)

### 4-2. OpenAI: 검색 대안과 원문 정리를 구분

**검색 대안:** Responses API에서 `web_search`를 지정하고 검색 출처 목록·인용 URL을 받습니다. 도메인 필터와 반환 길이·도구 호출 제한을 사용합니다. 모델이 반환한 후보는 같은 대기열로 보내고, 이름·일시를 바로 운영 DB에 쓰지 않습니다. 실제 검색 도구 호출 수를 기록합니다.

**원문 정리 보조:** 이미 합법적으로 읽을 수 있는 공지 텍스트를 별도 Responses 요청에 넣고 Structured Outputs로 다음 항목을 추출합니다. 검색 도구를 켜지 않고, 모델에는 DB 쓰기나 외부 이동 권한을 주지 않습니다.

| 항목 | 값과 검사 |
| --- | --- |
| `name`, `channelUrl`, `eventKind` | 원문에 있는 값. `FIRST_DEBUT/PLATFORM_DEBUT/TRANSFER/PREDEBUT/UNKNOWN` 구분 |
| `eventDate`, `eventTime`, `timezone` | 없으면 null. 글 작성일과 행사일 구분. KST 등 근거 필요 |
| `evidence` | 각 항목을 확인한 출처 URL, 본문의 짧은 근거 구간, 확인시각 |
| `missingFields`, `conflicts` | 빠진 항목·날짜 충돌·연기 가능성 |

저가 추출 모델 후보는 공식 모델 문서에서 구조화 출력을 지원하는 GPT-6 Luna입니다. **한국어 데뷔 공지 정확도는 아직 시험하지 않았습니다.** JSON 형식이 맞아도 사실이 맞다는 뜻은 아닙니다. 원문 구간과 값이 일치하는지 코드로 다시 검사하고 불명확하면 보류합니다. 원문 안의 ‘이전 지시 무시’ 같은 문구는 데이터로만 취급합니다. X 콘텐츠의 AI 전달은 해당 계약·원천 조건을 별도 확인하기 전 기본 비활성입니다. [모델 기능](https://developers.openai.com/api/docs/models/gpt-6-luna), [구조화 출력의 한계](https://developers.openai.com/api/docs/guides/structured-outputs)

### 4-3. X 공식 API: 주소 발견과 본문 확보

- 인증: 개발자 앱의 Bearer Token. 공개 공지 조회를 위해 모든 신인에게 개별 로그인 연결을 요구하는 구조는 아닙니다. 앱 접근·사용 조건은 적용됩니다.
- 발견: `GET https://api.x.com/2/tweets/search/recent`. 예시 검색식은 `(버튜버 OR 버츄얼) (데뷔 OR "첫 방송") (치지직 OR SOOP OR 숲) -is:retweet`. `lang:ko`는 다국어 공지를 놓칠 수 있어 일부 회차에만 사용합니다.
- 증분: 마지막 성공 시각/게시물 ID와 페이지 커서를 기록하고 약간의 중복 구간을 두어 수집합니다. 최근 7일보다 오래된 게시물은 Recent Search로 못 찾습니다. 게시물 작성일과 데뷔일은 별도입니다.
- 본문: 검색에서 받은 본문을 재사용하고 필요할 때만 `GET https://api.x.com/2/tweets/{id}` 또는 게시물 묶음 조회를 사용합니다. `tweet.fields`에 `author_id,created_at,entities,edit_history_tweet_ids` 등 필요한 값만 요청합니다.
- 링크: `entities.urls.expanded_url`에서 본인이 연결한 방송국을 찾습니다. 이름만 비슷한 채널을 연결하지 않습니다. 긴 글·인용·이미지의 전문이 항상 기본 `text`에 포함된다고 가정하지 않습니다.
- 작성자: 모든 결과에 유료 사용자 정보 확장을 붙이지 않고, 검증할 후보만 별도 사용자 조회를 합니다.
- 권리·운영: X 원문을 그대로 위키에 복사하지 않습니다. 공개된 본인 방송국 연결을 근거로 활동 프로필을 연결하며 개인정보·비공개 정보 추정을 하지 않습니다. 정정·삭제 요청과 콘텐츠 상태 변화에 대응할 기능이 필요합니다.

현재 정책은 공개 정보를 근거로 한 합리적인 계정 연결에 예외 조건을 두므로 ‘무조건 본인 동의 없이는 불가능’이라고 단정하지 않습니다. 반대로 API 키가 있다고 모든 광고 활용·프로필 가공이 허용된다고 단정하지도 않습니다. X는 비공식 브라우저 자동 조회를 제한합니다. [검색·인증 예시](https://docs.x.com/x-api/posts/search/quickstart/recent-search), [본문 조회](https://docs.x.com/x-api/posts/lookup/quickstart), [콘텐츠 정정·계정 연결 정책](https://docs.x.com/developer-terms/policy), [자동 조회 지침](https://docs.x.com/developer-guidelines)

### 4-4. 치지직: 찾은 방송국의 기본 프로필 확인

권장 경로는 `GET https://openapi.chzzk.naver.com/open/v1/channels`입니다. 등록한 앱의 `Client-Id`, `Client-Secret` 헤더를 사용하고 `channelIds`에 발견한 ID를 넣습니다. 한 번에 최대 20개입니다.

공식 응답의 채널 ID·현재 이름·프로필 이미지·팔로워 수 등을 확인합니다. **이 API는 데뷔일·국적·생일·상세 자기소개·신인 여부를 전부 제공하지 않습니다.** 기존 코드의 `api.chzzk.naver.com/service/v1/channels/{id}`는 웹 서비스 내부 경로이므로 정식 Open API와 구분합니다. 정식 응답에 없는 소개를 얻으려고 내부 API를 필수 대체 경로로 만들지 않습니다. 소개는 본인 공지나 공식 공개 프로필에서 근거가 있을 때만 채웁니다. [공식 채널 API](https://chzzk.gitbook.io/chzzk/chzzk-api/channel.md), [인증·도메인](https://chzzk.gitbook.io/chzzk/chzzk-api/tips.md)

다른 방법인 `GET /open/v1/lives`는 현재 방송 중인 채널을 찾을 수 있지만, 페이지당 최대 20개·시청자 수 내림차순입니다. 적은 수의 페이지만 조회하면 신인보다 대형 채널에 편향되고 데뷔 전 채널은 없습니다. 따라서 신인 발굴 주 경로로 전수 순회하지 않습니다. [공식 라이브 API](https://chzzk.gitbook.io/chzzk/chzzk-api/live.md)

### 4-5. SOOP·시트·일반 공식 웹사이트

- SOOP: 기존 웰컴버추얼 기간 일정 응답과 방송국 공개 정보 연동은 출처별 처리기로 격리합니다. 현재 코드의 `welcomevirtual.sooplive.com/api/api.php?work=getScheduleList...`, `chapi.sooplive.co.kr/api/{id}/station`은 **웹사이트 내부 경로**이며 정식 상업용 Open API 계약으로 표현하지 않습니다. 개발자 포털 공개 문서에서 이 경로의 지원을 이번에 확인하지 못했습니다. 허용 범위를 넘겨 확대하지 않습니다. [공식 일정 페이지](https://welcomevirtual.sooplive.com/), [개발자 포털](https://developers.sooplive.co.kr/)
- 시트: 기존 연결된 공개 CSV만 읽습니다. Google Sheets API·사용자 OAuth가 필요한 개인 시트로 범위를 넓히지 않습니다. 최초 발견과 1차 근거는 구분합니다.
- 공식 웹 공지: Workers `fetch`로 HTML을 받고 `HTMLRewriter`로 본문·링크·JSON-LD를 읽습니다. HTTP 응답 크기·이동 횟수·허용 도메인을 제한합니다. HTMLRewriter는 JavaScript 실행 후 생기는 본문을 만들어주지 않습니다. [공식 HTML 처리 기능](https://developers.cloudflare.com/workers/runtime-apis/html-rewriter/)
- 임의의 검색 URL을 즉시 서버에서 열지 않습니다. HTTPS·호스트·리다이렉트를 검사하고, 새 도메인은 지원·허용 범위 확인 전 대기합니다. 키가 든 요청을 다른 호스트로 재전송하지 않습니다.

## 5. 원문을 읽는 기술 비교

| 기술 | 적합한 곳 | 장점 | 문제·비용 | 적용 |
| --- | --- | --- | --- | --- |
| JSON·CSV 직접 읽기 | 공식 일정·공개 시트 | 빠르고 일관됨. AI 토큰 없음 | 응답 구조 변경 시 실패 | 우선 |
| fetch+HTMLRewriter | 정적 공식 공지·HTML 본문 | 브라우저 없이 처리. 낮은 부하 | 동적 본문·로그인 화면은 부족 | 기본 |
| 정규식·날짜 규칙 | 날짜·시간·채널 URL 추출 | 결정적이며 검사하기 쉬움 | 여러 멤버·상대 날짜·시간대 해석이 어려움 | 구조화 원천 중심 |
| OpenAI Structured Outputs | 읽을 수 있으나 형식이 다양한 글 | 자연어를 공통 항목으로 정리 | 환각·토큰·전송 조건. 사실 확정은 별도 | 월 한도 있는 보조 |
| 이미지 OCR·비전 | 데뷔 일시가 홍보 이미지에만 있는 경우 | 텍스트 누락 보완 | 글자 오인·장식 글꼴·인물 혼합. 이미지 취득 조건 | 첫 버전 제외, 보류 이유로 기록 |
| Browser Run+Playwright | 허용된 동적 공식 사이트 | 실제 렌더링된 페이지 처리 | 사이트별 유지보수·차단·실행시간·추가 호출 | 필요 사이트만 후순위 |

AI나 OCR을 빼면 자동 처리율이 낮아질 수 있습니다. 그렇다고 원문을 못 읽은 상태에서 검색 요약을 AI로 다시 정리해 ‘검증 완료’로 바꾸지 않습니다. 첫 버전은 텍스트로 명확한 후보부터 처리하고, 이미지 전용·모호한 공지의 비율을 측정한 뒤 확장합니다.

## 6. DB·등록·프로필·달력은 어떤 기술로 연결하는가

**수집 프로그램이 관리자 화면을 클릭해 등록하지 않습니다.** 기존 서버 내부 등록 함수를 재사용합니다. 운영 DB를 수정할 때마다 Cloudflare 관리 API나 관리자 로그인 자동화를 하는 구조도 피합니다.

1. 검색 결과는 기존 공지 대기열에 저장합니다. URL+출처+검색 키+확인 상태를 남깁니다.
2. 원문에서 추출한 후보는 내부 공통 형식으로 정규화합니다. 행사일과 게시일·확인시각을 각각 보관합니다.
3. 출처·채널·필수 항목 검증을 통과하면 서버 CSV에 F로 저장합니다. 서버 정본은 현재 D1의 CSV 원문·버전·해시입니다. PC 파일은 사본입니다.
4. CSV를 다시 읽고 내용 해시를 확인합니다. 플랫폼+고유 채널 ID로 공개·보조 채널·심사대기·CSV 중복을 검사합니다. 활동명은 중복 키가 아닙니다.
5. 저장 직전에 운영자 수정 여부와 기존 값이 바뀌지 않았는지 다시 확인합니다. 동일하면 건너뛰고 충돌하면 보류합니다.
6. 기존 `DiscoveryStore.publish()`에서 D1 binding의 `prepare().bind()`와 `batch()`로 프로필·채널 연결·변경 이력을 함께 반영합니다. CSV 영수증·잠금·기존 값 비교를 보존합니다.
7. 기존 서비스 바인딩으로 공개 프로필·행사 API를 다시 읽습니다. 현재 실행기의 `/api/v1/portal/profiles?version=3`, `/api/v1/events` 경로를 사용하고, 프로필 이미지·방송국·한국시간·기본 활동권역·행사 유형을 비교합니다. 기본 필터 노출은 기존 프런트엔드 달력 색인 규칙까지 확인해야 하며 API 응답에 이름이 있다는 사실만으로 완료 처리하지 않습니다.
8. 모두 맞으면 해당 CSV 제안만 T입니다. DB는 저장됐으나 공개 확인이 실패하면 재등록하지 않고 확인 단계부터 복구합니다.

**우리 달력은 외부 Google Calendar API가 아니라 저장된 프로필·일정에서 행사 데이터를 만드는 기존 서비스입니다.** 동일한 데뷔를 프로필·별도 달력 DB에 이중 입력하는 새 구조를 만들지 않습니다. 메인·달력·Header·Footer 디자인은 유지합니다. D1의 배치는 SQL 실패 시 롤백하지만, CSV 준비·DB 저장·HTTP 공개 확인 전체가 하나의 분산 트랜잭션은 아니므로 단계별 복구 상태가 필요합니다. [D1 배치 보장](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)

### 보관·처리 기술의 대안

| 선택 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| D1에 후보·작업 상태·CSV 원문 | 현재 구조 재사용. 조회·중복·잠금·버전 비교를 같은 DB에서 처리 | CSV 전체 버전 쓰기와 묶음 크기 한계 | 1차 유지 |
| D1에 행, R2에 CSV 버전 | 파일이 커질 때 DB 문자열 크기 부담 완화 | 업로드 성공 후 DB 포인터 갱신·고아 파일 정리 필요 | 실제 크기 증가 시 전환 |
| KV에 대기열·중복 판정 | 키 조회 단순 | 등록 경쟁·여러 값 원자 처리에 맞지 않음 | 공개 등록 기준 저장소로 쓰지 않음 |
| 기존 DB를 별도 Postgres로 이전 | 복잡한 관계·대규모 운영 선택지 | 이전 비용·운영 추가. 현재 문제를 직접 해결하지 않음 | 현재 제외 |

현재 앱의 CSV 묶음 512KiB 제한과 D1의 문자열/행 크기 한계는 별개입니다. 512KiB에 가까워지면 더 조사해도 CSV 선저장이 막힐 수 있으므로 크기 경보와 월별 분할/보관 전환을 먼저 준비합니다. 행을 버리거나 최초 작성일·T/F를 초기화해 해결하지 않습니다. [D1 한계](https://developers.cloudflare.com/d1/platform/limits/)

## 7. 자동 실행 기술 비교와 권장 구조

| 방식 | 장점 | 문제 | 적용 |
| --- | --- | --- | --- |
| Workers Cron+TypeScript+D1 대기열 | 기존 자원 재사용. PC 없이 실행. 비용 계수 통합 | 시간·조회 한도에서 다음 회차로 이월하는 코드를 직접 관리 | 1차 권장 |
| Cron+Cloudflare Queues | 후보별 독립 처리·재시도·실패 대기열 | 중복 전달을 전제로 구현. 소비자 전체에 공통 예산 필요 | 대기 지연이 지속되면 추가 |
| Cron+Cloudflare Workflows | 단계별 상태·재시도·대기·재개를 명시적으로 관리 | 인스턴스·단계 저장과 관측 비용, 기존 처리 이식 필요 | 여러 날 승인 대기·복잡한 복구가 커지면 검토 |
| 별도 서버+n8n/브라우저 자동화 | 시각적으로 흐름을 만들고 브라우저 연결하기 쉬움 | 서버·업데이트·보안·동시 실행 관리 추가 | 현재 제외 |
| PC 작업 스케줄러 | 초기 구성이 간단 | PC 종료 시 중단 | 기존 중지 유지 |

권장 연결은 `Cron → 검색 계획/예산 예약 → 원천별 수집 → D1 대기열 → 추출·검증 → CSV → 기존 등록기 → 공개 확인 → 실행 보고`입니다. 모든 단계는 같은 실행 ID를 사용합니다. API 호출·원문·상태 변경을 그 ID로 추적합니다. Queues/Workflows를 추가해도 월 사용량 한도가 자동으로 보장되는 것은 아닙니다.

예약은 한국 09시·21시, 월요일 10시입니다. Cloudflare Cron은 UTC이므로 각각 `0 0 * * *`, `0 12 * * *`, `0 1 * * MON`입니다. 원문 4회·검색 4회·고정 원천 12회·신규 상세 12회·기존 재확인 8회로 기존 총 40회 상한을 유지합니다. 선택한 AI 호출도 이 총량에서 차감하며 신규 상세 예산 안에 배정합니다. 월 최대 70회, CPU 5초·DB·CSV 상한을 유지합니다. [예약 규칙](https://developers.cloudflare.com/workers/configuration/cron-triggers/)

09시는 신규 발견·오늘~7일 후 공지를 우선, 21시는 미처리 원문·오늘~3일 후 변경을 우선합니다. 월요일은 전주~장기 누락 범위를 순환합니다. 전주 일정이 지났다는 것만으로 방송 완료를 표시하지 않습니다. 같은 사람의 등록을 반복하지 않고 검색 묶음과 대기 후보를 이어갑니다.

## 8. 비용 시뮬레이션과 상한

금액은 USD·세전, 환율 환산과 인건비 제외입니다. 계정의 다른 서비스 사용량과 합산되므로 포함량 잔여 여부는 실제 연결 전에 확인해야 합니다.

| 구성 | 계산 가정 | 예상 외부 서비스 사용료 |
| --- | --- | --- |
| A: Tavily 기본안 | Basic 월 280회, 무료 1,000크레딧 중 잔여량 사용 | 검색료 0달러. 무료 정책·잔여량 조건 |
| OpenAI 검색 대안 | 실제 웹 검색 도구 호출 월 280회 | 도구료 2.80달러+모델 입력·출력·검색 문맥 토큰 비용 |
| OpenAI 원문 추출 보조 | 월 300회, 회당 전체 입력 3,000토큰·전체 청구 출력 600토큰, Luna 일반 단가 입력 0.10/출력 0.50달러 per 1M | 약 0.18달러. 사고·내부 출력 등 실제 토큰이 늘면 증가. 월 1달러 앱 상한 제안 |
| B: X 확장 | 게시물 최대 800개 읽기+사용자 최대 50개 읽기. 검색·본문·재확인을 합산 | 800×0.005+50×0.010=4.50달러. 기타 리소스 요청을 끄고 월 5달러 앱 한도 제안 |
| Browser Run 선택 확장 | 월 100페이지×브라우저 20초 가정 | 약 0.56브라우저 시간. 기존 포함량 안이면 추가 시간료 0달러이나 다른 사용량·동시성 별도 |

OpenAI 추출 비용은 검색 도구를 끈 텍스트 처리 계산입니다. 월 300회는 상한 예시이며 회차 외부 요청 예산 때문에 실제 처리 가능량은 더 작을 수 있습니다. [OpenAI 요금](https://developers.openai.com/api/docs/pricing), [Tavily 요금](https://docs.tavily.com/documentation/api-credits), [X 리소스 단가](https://docs.x.com/x-api/getting-started/pricing), [브라우저 요금](https://developers.cloudflare.com/browser-run/pricing/)

X 검색은 ‘검색 요청 1회=0.005달러’가 아닙니다. 결과 게시물 수·확장 사용자 등의 리소스로 과금됩니다. `max_results=10`이어도 사용자 확장을 붙이면 비용이 늘 수 있습니다. 같은 UTC 일자 중복 할인은 공식적으로도 예외 가능성이 있어 우리 한도 계산에는 할인 없이 잡습니다. 과거 7일 게시물 검색으로 세 달 뒤 데뷔 공지도 찾을 수 있지만, 그 공지가 7일 안에 작성됐어야 합니다.

### Cloudflare 자체 사용량

- 기존 계정이 Workers Paid이면 신규 Worker 하나마다 기본 5달러를 추가하는 구조로 계산하지 않습니다. 유료 계정을 새로 시작해야 한다면 기본 요금 월 5달러부터 고려합니다. 현재 청구 계정을 이번에 조회하지 않았습니다.
- 현재 상한 70회×CPU 5초=월 350,000 CPU ms, D1 읽기 210만행·쓰기 49,000행입니다. 마감 기록·색인·정리 등 실제 메타데이터는 별도 여유를 봐야 합니다.
- Paid 포함량 잔여가 충분하면 이 작업의 증분 실행·읽기·쓰기 요금은 0달러일 수 있습니다. 포함량이 이미 소진됐다는 가정에서 위 CPU·행 사용량만 단가로 계산하면 약 0.06달러입니다. **저장 공간·로그·페이지 방문 트래픽·기존 서비스는 이 숫자에 포함되지 않습니다.**
- CSV 회차 쓰기 상한 4MiB×70회=월 최대 280MiB의 버전 쓰기량입니다. 이는 현재 저장량이 아니며 보관 버전이 누적되면 공간 비용이 증가합니다. 90일 정리 대상이라도 현재 정본·복구 참조 버전은 보호하므로 실제 잔존량을 별도 관찰합니다.
- Queues는 Paid 월 100만 작업 포함, 초과 100만당 0.40달러입니다. 통상 메시지 하나의 쓰기·읽기·삭제는 3작업이며 재시도는 추가됩니다. Workflows는 Workers의 요청·CPU와 별도 상태 저장 사용량을 함께 계산합니다. 1차에서는 둘 다 추가하지 않습니다.

공식 근거: [Workers 요금](https://developers.cloudflare.com/workers/platform/pricing/), [D1 요금](https://developers.cloudflare.com/d1/platform/pricing/), [Queues 요금](https://developers.cloudflare.com/queues/platform/pricing/), [Workflows 요금](https://developers.cloudflare.com/workflows/reference/pricing/). 무료 Worker의 CPU·DB 호출 제한과 현재 5초·220호출 설계를 혼동하면 안 됩니다.

### 비용을 실제로 막는 방법

1. 호출 전에 D1에서 회차·월 사용량을 원자적으로 예약합니다. 결과를 못 받아도 예약량을 되돌리지 않습니다.
2. Tavily는 Basic 고정·고급 자동 선택 끔·월 280크레딧·종량제/자동 충전 끔을 기준으로 합니다.
3. X는 응답 결과 최대치와 사용자 확장 비용까지 최악값으로 예약하고 5달러를 넘길 요청을 보내지 않습니다. 유료 기능은 아직 개설하지 않았습니다.
4. OpenAI 추출은 전체 입력 길이·출력 토큰 제한·월 1달러를 함께 적용합니다. 제한된 길이로 증거가 부족해지면 승인하지 않습니다.
5. API가 401/403이면 인증·권한 실패, 429이면 한도/호출 제한으로 기록하고 무한 재시도하지 않습니다. 다른 업체 유료 호출로 자동 전환하지 않습니다.
6. 업체의 요금 변경·추가 리소스 청구·다른 계정 사용량까지 앱 코드가 보장하지는 못합니다. 공급자 사용 제한·자동 충전 해제·청구 확인을 함께 사용합니다. 수치 예산을 계정 전체 절대 청구 상한이라고 표현하지 않습니다.

## 9. 예상 문제와 대응

| 문제 | 발생 영향 | 대응 |
| --- | --- | --- |
| 검색에 색인되지 않은 새 공지 | 신인 미발견 | SOOP 일정 병행, X 공식 검색 선택, 누락 기간 순환. 전수 수집 보장 금지 |
| X 주소만 찾고 본문을 못 읽음 | 후보만 쌓이고 등록 안 됨 | X 공식 API 모듈 또는 별도 본인 공식 원문. 무료 검색만으로 해결됐다고 보고하지 않음 |
| ‘첫 방송’이 플랫폼 이적임 | 잘못된 첫 데뷔 소개 | 행사 범위 분리. 과거 이력 없음/firstBroadcastDate null을 신인 증거로 사용하지 않음 |
| 이미지에만 날짜가 있음 | 텍스트 추출 불가 | 이미지 전용 보류. OCR·비전은 별도 성능 시험 뒤 도입 |
| 여러 멤버·여러 날짜 | 다른 사람 시간 연결 | 멤버별 채널 ID와 해당 문장/행을 연결. 하나라도 모호하면 보류 |
| 자동 등록 기준이 과도하게 엄격함 | 수동 대기 증가 | 보류 사유별 비율 측정. 근거가 충분한 공개 한국어 공지의 시간대 판단 등 별도 기준을 결정하고 시험. 추측으로 조건 완화하지 않음 |
| 공지 연기·취소·삭제 | 달력이 오래된 상태 | 임박 일정 우선 재검사. 명시 변경과 단순 조회 실패 구분. X 콘텐츠 정정·삭제 요구는 별도 처리; 소스 부재만으로 프로필 전체 삭제하지 않음 |
| 월 280개 검색·원문 4회가 부족 | 미처리 증가 | 최고 대기시간·도메인별 실패·최초 발견 지연 측정. 한도 확대 전 중복 검색과 낮은 가치 원천 축소 |
| 월 70회가 시험으로 소진 | 정규 예약이 중단될 수 있음 | 잔여 정규 슬롯을 계산해 시험 예약을 거절하는 보호 추가. 31일+월요일 5회면 정규 67회라 시험 여유 3회뿐 |
| 원문 조회 허용 도메인이 제한됨 | 검색 링크를 찾아도 서버가 거부 | 도메인별 지원 등록. 임의 링크 전면 허용 금지. 신규 출처 적용 작업을 보고서에 남김 |
| 서버가 중간에 종료 | 일부 저장·재등록 위험 | 검색·CSV·공개 상태를 분리하고 중복 키·내용 비교·복구 영수증으로 마지막 단계부터 재개 |
| 이미지 로딩만 확인 | 부적절한 이미지 내용 통과 가능 | 로딩 검사와 내용 검토를 구분. 기존 공개 콘텐츠 검토 기준을 적용하고 애매한 경우 보류 |

사용자가 사이트를 열 때마다 검색하거나 원문을 읽지 않습니다. 홈페이지는 승인된 DB만 조회하므로 수집 API 수가 곧 페이지 로딩 비용으로 늘어나는 구조가 아닙니다. 긴 원문·검색 전체 응답·원본 이미지를 기본 페이지 응답에 넣지 않습니다.

## 10. 개발 목록과 완료 기준

| 순서 | 만들거나 수정할 부분 | 완료 기준 |
| --- | --- | --- |
| 1 | 검색 계획·월 비용 예약·정규 회차 보호 | 날짜 경계·동시 실행·시험·재시도를 포함해 한도를 넘기지 않음 |
| 2 | Tavily 공통 검색 연결·URL 대기열 | 실제 이름 없는 검색어와 새 출처 주소를 기록. 검색 실패를 신규 0명 성공으로 바꾸지 않음 |
| 3 | 출처별 fetch/파서·채널 공식 API 연결 | 본문 부족·차단·응답 변경·미지원 도메인을 구별. 없는 프로필 항목은 비움 |
| 4 | 항목별 근거와 검증 상태 | 이름·행사·일시·채널을 출처 문장/행과 연결. 사람의 판단은 예외로 한정 |
| 5 | 기존 CSV·중복·공개·복구 재사용 | CSV 저장 실패 시 공개 없음. 운영자 수정 덮어쓰기·동일 채널 재등록 없음 |
| 6 | 선택 기능: X API 또는 AI 추출 | 서비스별 권한·비용 설정·삭제/정정·오류 시험을 통과. 자동으로 켜지지 않음 |
| 7 | 실제 검색·정기 실행 시험 | 사전에 이름을 넣지 않은 신규 채널로 발견→근거→CSV→DB→프로필·달력까지 증거 확보 |

### 시험 보고에 반드시 포함할 것

- 검색 입력, 조사 기간, 발견 출처 URL, 원문 확인시각, 발견 시점 DB·CSV·심사대기 비교 결과.
- 검색 원문과 확정값이 어떻게 연결됐는지, 이미지·채널·시간대 검증 결과.
- 새 주소·기존 재발견·신규 고유 채널·신규 공개·기존 수정·보류·실패를 분리한 수치.
- 다음 회차에서 미완료를 이어받고 등록을 중복하지 않는 결과.
- 공급자별 요청·토큰/리소스·예산 잔여, DB 행·CSV 크기·최고 대기시간.
- 키 없음·429·X 차단·시간 누락·채널 충돌·CSV 실패·DB 실패·달력 불일치 때의 동작.

검색 업체별 실제 발굴 성능과 자동 승인 비율은 아직 측정하지 않았습니다. 임의의 성공률·매달 발견할 신인 수를 넣지 않습니다. 1차 개발은 위 공정을 연결하는 작업이고, 시험은 해당 기술 조합이 우리 자료에서 쓸모 있는지 확인하는 단계입니다.
