## 1 무엇을 먼저 개발할 것인가

**기존 조사 결과를 재사용해 새 후보를 찾고, 데이터를 자동 보강하며, 조건에 맞는 소개를 공개하고 계속 갱신하는 기반이 첫 개발이다.** D0~D6가 첫 출시 묶음이다. 오늘의 발견·확장 관심 피드·채팅·게임은 뒤로 옮긴다.

사용자와 Codex가 함께 개발하므로 인건비·외주 개발비·시간당 비용을 금액에 넣지 않는다. 다만 직접 판단/개발/운영해야 할 작업과 시간 부담은 별도로 드러낸다. 아래 일정은 순서이며 달력상 납기나 개발 착수 승인이 아니다.

## 3 직접 검토 시간의 계획

출처 선정·공식성/허용 항목·대표작 기준·동일 인물 병합·소속/데뷔일 충돌·권리/삭제는 직접 판단이 남는다. 사이트마다 파서를 계속 수리하고 모든 신인 영상을 보며 소개문을 쓰는 운영은 필수로 넣지 않는다. 유료 OCR·AI 호출도 필수 아님.

작업량 예시: 주 100건 중 예외 20건×3분 + 표본·소스 확인 30분 = 주 90분. 예외가 50건이면 주 180분이다. 후보량·예외율·시간은 모두 가정이며 실측 후 변경한다. 예외가 늘면 출처·규칙을 좁히고 중복/보강 오류를 먼저 해결한다. 인건비를 제외해도 이 직접 작업이 없어지는 것은 아니다.

## 4 서버·DB·외부 서비스의 지출 항목

현재 계정·최신 가격·청구·할당량을 외부 조회하지 않았으므로 확정 월 견적을 제시하지 않는다. 공개 URL의 접근 가능성을 무제한 무료 API 계약으로 가정하지 않는다.

| 비용 항목 | 첫 출시 방식 | 실제 돈이 늘어나는 조건 |
| --- | --- | --- |
| 웹/API·정기 수집 실행 | 기존 Cloudflare Worker 우선, 단일 예약 실행·배치. 상시 별도 서버 없음 | 기존 플랜 포함 요청·CPU/실행 한도 초과 또는 플랜 변경 |
| DB | 기존 D1에 필요한 논리 영역 연결, 변경분·작업 상태만 저장 | 계정 잔여 읽기·쓰기·저장량 초과. 인덱스·로그·삭제 포함 |
| 공식 정보 조회 | 기존 채널/미디어 조회와 허용된 구조화 소스 재사용 | 특정 API의 유료 계약 필요·쿼터 증설. 미확인 유료 API는 자동 활성화하지 않음 |
| X·외부 검색 | 유료 검색 계약은 첫 출시 필수에서 제외 | 도입을 결정한 경우 별도 견적. 미도입이면 해당 계약비 0원이며 전체 검색 자동화는 제공하지 못함 |
| GitHub Actions·보고 산출물 | 기존 보고 도구 재사용 가능. Worker와 이중 수집 금지 | 계정/저장소의 실행·산출물 포함량 초과. 저장소 공개 여부/무료량을 임의 가정하지 않음 |
| 이미지·영상·전송 | 허용된 이미지 참조·원문 링크·공통 기본 이미지. 원본 복제/영상 호스팅 없음 | 이미지 프록시·자체 저장/전송이 필요하면 별도 용량·요금 추가 |
| 로그·백업·도메인 | 기존 운영 항목, 필요 최소 로그·내보내기 | 보관/저장/실행 초과 또는 도메인 갱신. 기존 비용 중복 합산 금지 |
| 외부 AI·SSAPI·벡터 DB·아트 | 도입하지 않음 | 해당 신규 계약 비용 0원. 인건비와 외주 개발비도 산정 제외 |

'추가 계약비 0원'은 사이트 전체 운영비 0원이 아니다. 기존 기본료와 기존 방송 통계·이미지·웹 트래픽 비용은 계속 남는다.

## 5 치지직 미등록 채널 탐색을 포함한 수집량 재산정

첫 100개 관리 인물과 확장 1,000개를 비교하는 **설계 예산 시나리오**다. 실제 DAU·적중률·신규 확보 수·성장 예측이 아니다. 탐색 대상과 지원 페이지·검색 범위/이용 조건은 아직 외부 확인하지 않았다. 기존 방송 통계·현재 전체 서비스 사용량은 별도로 합산한다.

### 5.1 추가 발견 요청과 기존 수집의 구분

| 추가 치지직 탐색 | 가정 | 재시도 전 월 요청 |
| --- | --- | --- |
| 방송 목록 | 하루 6회×최대 20페이지 | 3,600회 |
| 채널 검색 | 검색어 8개×최대 2페이지×하루 3회 | 1,440회 |
| 추가 발견 요청 D | 위 합계. 페이지 지원 범위·한도 내 실행 | 5,040회 |
| 논리 실행 H | 방송 180회+검색어별 720회 | 900건 |

페이지당 방송 50·검색 20항목을 가정하면 응답 슬롯은 월 최대 208,800개다. 반복 채널을 포함하므로 유일 인물·보강 후보·DB 저장량으로 환산하지 않는다. 실행별 중복 제거·단서 선별·짧은 재확인 캐시 후 묶음 대조하고, 이월·잘림·후속 보강 한도를 기록한다.

H는 소스/검색어 작업 상태의 기록 단위다. 한 예약 실행에 여러 작업을 묶을 수 있어 **외부 HTTP 요청·논리 작업·Worker 실행 과금 요청은 같은 수가 아니다.** 기존 통계 응답과 공유되는 요청의 차감은 아직 검증되지 않아 0으로 둔 보수적 계산이다. 실제 공유 시 차감하되 같은 소스 수집을 이중 실행하는 설계를 목표로 삼지 않는다.

| 입력 | 초기 100명 관리 | 확장 1,000명 관리 |
| --- | --- | --- |
| 기타 목록 소스 S / 목록 확인 F | 10개 / 600회 | 30개 / 1,800회 |
| 채널 확인 U: 60% 하루 2회·40% 월 4.3회 | 3,772회 | 37,720회 |
| 새 치지직 발견 요청 D / 논리 실행 H | 5,040회 / 900건 | 5,040회 / 900건 |
| DB 대조·관측 처리 K | 6,000회 | 12,000회 |
| 발견 원시 후보 I | 600건 | 2,400건 |
| 최초 상세 보강 C (건당 3요청) | 90건 / 270요청 | 450건 / 1,350요청 |
| 기존 인물의 변경 반영 J | 120건 | 1,200건 |
| 사이트 조회 V | 27,000회 (DAU 300×하루 3회×30일) | 270,000회 (DAU 3,000×하루 3회×30일) |

F=S×하루 2회×30일이며 **S/F에는 새 치지직 방송/채널 검색을 넣지 않는다.** 확장 시에도 D는 같은 탐색 상한을 유지하며 관리 인물 수가 10배라고 검색량을 자동으로 10배 늘리지 않는다. K는 배치/기간별 중복 제거 후 DB 대조 수이고 같은 채널의 다른 회차도 포함한다. I/C는 누적 후보 수가 아닌 월 처리 예산이며 208,800 응답 슬롯 대비 실제 적중률을 예측한 값이 아니다.

### 5.2 변경 전후 외부 요청

```text
새 기본 외부 요청 Q0 = F + U×2 + C×3 + D
초기 Q0 = 600 + 3,772×2 + 90×3 + 5,040 = 13,454회
초기 재시도 여유 ceil(Q0×10%) = 1,346회 → 총 14,800회/월
확장 Q0 = 1,800 + 37,720×2 + 450×3 + 5,040 = 83,630회
확장 재시도 여유 = 8,363회 → 총 91,993회/월
```

| 월 계획치 | 개정 전 v3.0 | 개정 후 v3.1 | 증가 |
| --- | --- | --- | --- |
| 초기 수집 요청 | 9,157회 | 14,800회 | +5,643회 (약 61.6%) |
| 확장 수집 요청 | 85,954회 | 91,993회 | +6,039회 (약 7.0%) |

추가 발견 자체는 재시도 전 5,040회이고, 재시도 10%를 별도 잡으면 5,544회다. 위 증가량에는 최초 상세 보강을 60→90건·300→450건으로 늘린 양과 전체 재시도 재계산까지 포함한다. 단순히 기존 총량에 5,040만 더하지 않는다.

채널 확인당 2요청·최초 보강당 3요청은 가정이다. 추가 본문 페이지·외부 유료 검색·다중 플랫폼 조회·이미지 프록시 등은 별도 초과 요인이다. 재시도 10%는 예산 여유이며 실제 장애/권한 실패 시 무조건 재호출하는 정책이 아니다. 권한 실패는 중지한다.

## 6 DB·저장·CPU 사용량 재산정

대량 목록은 메모리에서 회차 내 중복을 제거하고 필요한 채널만 DB 대조한다. 원시 응답 전체·반복 이미지·무변화 콘텐츠를 계속 저장하지 않는다. 다만 대조 상태와 최소 관측 기록·커서·후보·근거·인덱스·삭제는 비용에 포함한다.

```text
읽기 R = U×6 + I×8 + F×4 + C×12 + V×캐시미스 10%×20행 + K×4 + H×4
초기 R = 22,632 + 4,800 + 2,400 + 1,080 + 54,000 + 24,000 + 3,600
       = 112,512행/월
확장 R = 226,320 + 19,200 + 7,200 + 5,400 + 540,000 + 48,000 + 3,600
       = 849,720행/월

쓰기 W = U×2 + F×2 + I×8 + C×12 + J×8 + K×2 + H×2 + 예외/로그/만료 E
초기 E=6,000: W = 7,544 + 1,200 + 4,800 + 1,080 + 960 + 12,000 + 1,800 + 6,000
                  = 35,384행/월
확장 E=20,000: W = 75,440 + 3,600 + 19,200 + 5,400 + 9,600 + 24,000 + 1,800 + 20,000
                   = 159,040행/월
```

K의 계수는 대조/관측 처리에 읽기 4행·쓰기 2행을 예약한 것이며 실제 SQL/인덱스 과금량이 아니다. H는 실행/커서 상태, U/F는 관측 상태, I/C/J는 후보·근거·채택·반영 이력 계수다. 재시도 결과·제한 로그·만료 삭제는 E에 포함한다. 실제 스캔·인덱스 쓰기·캐시 실패·큐 이월이 다르면 사용량을 보정해야 한다.

| 월 신규 기능 예산 | 초기: 개정 전 → 후 | 확장: 개정 전 → 후 |
| --- | --- | --- |
| DB 읽기 | 82,152 → 112,512행 (+30,360) | 789,120 → 849,720행 (+60,600) |
| DB 쓰기 | 15,824 → 35,384행 (+19,560) | 119,240 → 159,040행 (+39,800) |
| 신규 저장 관리 공간 | 0.03~0.10 → 0.05~0.15GB | 0.20~0.50 → 0.25~0.75GB |

저장 공간은 후보/근거·최소 관측 상태·공개 보강·메타데이터·반영/동기화·인덱스 여유를 포함한 관리 예산이다. 기존 전체 DB·방송 원자료·별도 백업은 제외다. 미해결 후보/최근 활동 90일·상세 실행 로그 30일의 초깃값을 전제로 하며 채택 근거·장기 이력 누적은 별도 추적한다. 출처 보관 조건이 더 짧으면 우선 적용한다.

추가 탐색 5,040회와 재시도 여유를 합친 5,544회에 대해, 외부 요청당 처리 CPU가 10/50/200ms라고 가정하면 월 55,440/277,200/1,108,800ms(약 55초/4.6분/18.5분)다. **실측값·요금 예측이 아닌 민감도 예시**이며 배치 중복 처리·DB/보강·기존 API의 CPU는 별도다. 네트워크 대기 전체를 CPU로 계산하지 않는다. 실제 실행당 CPU/메모리 제한·최대 응답·중첩 요청 한도에 맞춰 배치를 분할할 수 있어야 한다.

## 7 실제 비용·예산·집행 조건

추가 호출이 약 61.6% 늘었다고 초기 청구액도 같은 비율로 늘어나는 것은 아니다. 기존 포함량·공유 잔여량·API별 계약·실행 CPU가 비용을 결정한다. 현재 계정·최신 단가·외부 이용 범위를 조회하지 않아 금액을 확정하지 않는다.

```text
DB 순증료 = max(0, R-계정 잔여 읽기)×읽기 단가
          + max(0, W-계정 잔여 쓰기)×쓰기 단가
          + max(0, 신규 저장-계정 잔여 저장)×저장 단가
전체 월 실비 = 기존 기본료 B + 필요한 플랜 차액 + DB 순증료
             + 실제 Worker 요청/CPU 초과 + 소스별 API/전송/로그/백업/Actions 초과
치지직 탐색에 따른 추가 실비 = 개정 후 실비 - 개정 전 실비
```

| 상황 | 추가 수집 반영 후 비용 판단 | 해야 할 일 |
| --- | --- | --- |
| 개정 후 요청·DB·CPU가 기존 포함량에 들어감, 유료 API 미도입 | 새 계약비 없이 순증 0원 가능. 현재 확정 아님 | 실제 계정 잔여량과 실행 CPU 대입 |
| 포함량 초과 또는 플랜 변경 필요 | 실제 초과량/단가·플랜 차액만 추가 | 이전 시나리오와 비교하고 탐색 페이지·횟수·보강 상한 조절 |
| 외부 홍보 검색의 유료 API 도입 | 별도 계약/쿼터 비용 추가, 이번 5,040회 예산에 포함 안 됨 | 도입 전 별도 결정. 미연결이면 직접 공식 링크 조사 |
| 기존 내부 추가 예산: 초기 월 1만원·확장 월 3만원 | 검토 기준선으로만 보존. 추가 탐색을 이 금액으로 수용 가능한지 미확인 | 실제 단가/잔여량으로 재산정 후 유지·상향·범위 축소 결정 |

**월 1만원/3만원은 공식 가격 기반 견적도 결제 차단 상한도 아니다.** 추가 수집량만 근거로 임의의 새 월 정액을 만들지 않는다. 유료 X/검색·SSAPI·외부 AI·전용 상시 서버·벡터 DB·외주 아트는 첫 출시 필수 계약에서 제외하며 인건비도 제외한다.

비용표의 미확인 입력은 B·현재 공유 잔여량·과금 단가/확인일·CPU·추가 플랜·API 이용료다. 실행이 허용된 단계에서만 확인한다. 세금·환산·해외 수수료·도메인 갱신·로그/백업/보고 저장도 필요한 경우 합산한다. 수집 중지·한도·이월은 비용 완화 장치이며 사업자 청구 상한을 보장하지 않는다.

## 8 홈페이지가 무거워지지 않게 할 구조

수집은 예약 배치로 실행하고 화면은 마지막 정상 공개 스냅샷·캐시를 읽는다. 수집 실패가 도감·상세의 전체 실패로 전파되지 않게 한다. 실제 현재 LIVE 상태와 오래된 공개 소개는 서로 다른 신선도 정책을 적용한다.

도감은 요약·페이지 단위, 상세는 필요한 콘텐츠만 제공한다. 전체 인물의 작품·근거·로그를 첫 화면에 합치지 않는다. 이미지 지연 로딩·플레이어 선택 재생·기존 코드 분할을 유지한다. 개발 후 기존 화면과 실제 요청/DB 행/CPU/지연을 비교하며 이번 문서 작성으로 성능 개선 완료를 주장하지 않는다.

## 9 확인할 핵심 실패 시나리오

중복 보고/재시도, 동명이인, 같은 채널의 다른 행사, 미확인 시간, 이전 수동 수정과 충돌, 삭제 후 재발견, 공식 채널 오연결, 한 소스 장애/부분 페이지, 비용 한도 도달, 반영 중 실패와 복구를 확인한다. 소스 테스트는 고정 예시부터 수행하고 실제 외부 연결은 실행 허용 범위가 열린 뒤 한다.

메인 하이라이트·실제 캘린더·PortalStage·공통 Header/Footer는 그대로 유지한다. 이 문서와 연결 문서만 작성했으며 코드·CSV·DB·계정·운영 설정을 변경하지 않았다.
