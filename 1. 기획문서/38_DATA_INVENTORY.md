# 38. 데이터 현황 — 지금 DB로 측정할 수 있는 것과 빈 곳

- 점검일: 2026-11-17 (마이그레이션 전체와 실제 쓰기·읽기 코드를 대조)
- 목적: 빅데이터 분석의 출발점으로 "무엇이 쌓이고 있고, 무엇을 잴 수 있고, 무엇이 비어 있는지"를 정리한다.

## 1. 실제로 쌓이고 있는 데이터

| 묶음 | 테이블 | 주기·범위 | 담기는 것 | 보관 |
|---|---|---|---|---|
| **방송 기록** (핵심) | `analytics_broadcast_runs` · `analytics_broadcast_snapshots` | 10분마다. 치지직 시청자 상위 100개 방송, SOOP 등록 채널(최대 150곳) | 채널 키·이름·주소·이미지, 방송 제목, 카테고리(게임), **시청자 수**, 방송 시작 시각(치지직만), 태그(치지직, 0064 적용 후) | 90일 |
| **버튜버 정보** | `streamerChannel` · `streamerChannel_info` · `portal_profiles` | 등록·수정 때 | 이름, 플랫폼·채널 주소, 소속, 국가, **데뷔 일시**·시간대, 소개, 이미지, X·홈페이지·팬카페, 그룹, 주요 콘텐츠·방송 언어, 영상·공지 | 계속 |
| **운영 기록** | `portal_requests` · `portal_profile_history` · `debut_submissions` · `crawler_update_logs` | 신청·문의·수정 때 | 신청 종류·시각·처리 상태, 수정 전후 내용, 자동 조사 결과 | 문의 1년, 나머지 계속 |
| **예전 수집기** (중복) | `analytics_live_snapshots` · `analytics_market_hourly` | 매시간, 치지직 상위 100개 | 방송 기록과 거의 같은 내용 | **정리 없음(계속 늘어남)** |
| 디스코드 | `discord_subscribed_channels` · `discord_streamer_verifications` | 연동 때 | 구독 서버, 채널 인증 | 계속 |
| 응원(개발 사이트만) | `cheer_logs` | 응원 때 | 하루 응원 기록 | 계속 |

만들어 두었지만 쓰지 않는 테이블: `analytics_channels`(팔로워 수 칸 있음), `analytics_live_sessions`, `analytics_category_map`, `analytics_opportunity_scores`, `users`, `reminders`, `verifications` 등.

## 2. 지금 측정할 수 있는 것

### 2.1 스트리머(채널) 단위
| 지표 | 계산 근거 | 한계 |
|---|---|---|
| 방송 횟수·방송 시간 | 10분 기록에 나타난 방송 ID·횟수 | 치지직은 상위 100위 안에 있을 때만 |
| 평균·최고 시청자, 시청자 추이 | 회차별 시청자 수 | 위와 같음 |
| 방송 시간표(요일×시간), 평균 방송 길이, 쉬는 날 | 기록 시각(한국 시간) | 위와 같음 |
| 콘텐츠 비중, 콘텐츠별 평균 시청자 | 카테고리 + 시청자 | SOOP은 카테고리가 비는 경우 많음 |
| 제목 키워드 | 방송 제목 | — |
| 태그 | 치지직 태그 | 0064 적용 이후부터 |
| 데뷔 후 성장·같은 달 데뷔 대비 순위 | 데뷔일(버튜버 정보) + 방송 기록 | 치지직 신입은 기록이 비어 있음 |
| 상위 100 진입 횟수·순위 | 회차별 순위 | 치지직만 |

### 2.2 게임(카테고리) 단위
시청자 합, 방송 수, 방송당 시청자, 경쟁 정도(여유·보통·혼잡), 시간대·요일별 수요, 급상승, 게임별 상위 채널, 새로 들어온 채널, 버튜버 비중.

### 2.3 태그 단위
태그별 시청자·방송 수, 함께 쓰인 태그, 태그 추이(저장 시작 이후).

### 2.4 시장(플랫폼) 단위
치지직 상위 100 시청자 합과 평소 대비, 오늘 최고, 시청자 1,000명 이상 방송 수, 상위 10개 집중도, 시간대별 흐름. (치지직 상위 100 기준이며 플랫폼 전체가 아님)

### 2.5 데뷔·버튜버 생태계 (방송 기록 없이도 가능)
월·주별 데뷔 수, 플랫폼별 데뷔 비중, 소속사별 데뷔, 국가, 데뷔 요일·시각 분포, 일정 미정 비율. 방송 기록과 합치면 데뷔 후 30일 방송 지속률(꾸준히 방송하는 비율)까지.

### 2.6 서비스 운영
등록 신청 수, 문의 유형, 처리 시간, 정보 수정 빈도. (방문자 행동은 DB가 아니라 Google Analytics)

## 3. 빈 곳 — 빅데이터 분석을 위해 채워야 할 것

| # | 빈 곳 | 영향 | 해결 | 무료 플랜 영향 |
|---|---|---|---|---|
| 1 | **치지직 신입 버튜버 기록 없음** (상위 100위 밖) | 프로필 분석 ②~⑤가 비어 있음 | 등록 버튜버 채널 직접 확인(15~20분 간격) | 쓰기 하루 수천 행 |
| 2 | **기록이 90일 뒤 사라짐** | 장기 성장·계절 추세 분석 불가 | **채널별 하루 요약 테이블**(방송 시간·평균·최고·주요 콘텐츠)을 만들어 영구 보관. 원본은 90일 | 하루 수백 행, 1년 수 MB |
| 3 | **팔로워 수 기록 없음** (그때그때 조회만) | 팔로워 성장 분석 불가 | 등록 버튜버 팔로워 수를 하루 한 번 저장 | 하루 150행 안팎 |
| 4 | **태그 저장이 마이그레이션 대기** (0063·0064 미적용) | 태그 추이가 쌓이지 않음 | `npm run db:migrate:live --prefix backend` 실행(계정 주인) | — |
| 5 | **SOOP 수집 불완전** (한 번에 150곳 조회, 무료 한도 50회) | SOOP 통계 준비 안 됨 | 나눠서 조회 | 쓰기 변화 없음 |
| 6 | **예전 수집기 중복** (매시간 100행, 정리 없음) | 쓰기·저장 공간 낭비, 500MB 한도 위험 | 사용처 확인 후 중단, 남은 자료 정리 | 하루 2,400행 이상 절약 |
| 7 | 채팅·커뮤니티 | 없음 | 보류(36·28·29번 검토 참고) | — |

## 4. 권장 순서

1. 0063·0064 마이그레이션 적용(태그 기록 시작) — 계정 주인 실행
2. 예전 수집기 중단(쓰기·저장 공간 확보)
3. 등록 버튜버 직접 기록 + SOOP 나눠서 조회
4. 채널별 하루 요약 테이블 + 팔로워 수 하루 1회 저장 (장기 분석의 바탕)
5. 프로필 보강(성장 곡선·방송 시간표·콘텐츠별 반응) 개발
