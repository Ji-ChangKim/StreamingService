## 1. 원인과 적용 내용

| 확인된 원인 | 적용한 최적화 |
| --- | --- |
| 각 달력 셀에서 전체 소개를 다시 탐색하고 날짜 포맷터를 반복 생성 | 현재 필터·시간대별 날짜/월 색인을 한 번 생성하고 재사용 |
| 쇼케이스도 프로필마다 시간 포맷터를 생성 | 달력·일정·쇼케이스에서 동일 포맷터를 공유. 최대 24개만 보관 |
| 메인 진입 시 등록·관리·통계·정책 화면 코드도 함께 로드 | 화면별 동적 import와 Suspense 적용. 공통 헤더는 화면 코드 다운로드 중에도 표시 |
| 개발 화면을 선택하기 위한 추가 진입점 다운로드 | 개발 HTML은 `portal-main.tsx`에서 직접 시작하고 초기 모듈을 병렬 preload |
| 소개가 필요 없는 화면도 전체 목록을 조회 | 캘린더·탐색·관심 목록·상세에서만 조회. 30초 이내 왕복은 같은 상태 참조 재사용 |
| 통계 집계의 여러 창 정렬과 중간 자료가 큼 | 마지막 제목과 다음 관측 시각의 정렬 방향 통일. 이미지·URL·중복 제목·원본 카테고리 ID를 중간 결과에서 제외 |
| 통계 진입 후 같은 방송 기록을 별도 재집계 | 요약에 포함된 기록으로 첫 25건을 구성. 같은 정렬과 커서로 다음 페이지 연결 |
| 공개 조회를 매번 DB에서 실행 | 소개 30초, 통계/방송 이력 120초 Cache API 적용. 조건·커서·조회 기준 시각을 캐시 키에 포함 |
| 정적 파일의 브라우저 캐시가 명확하지 않음 | 해시가 있는 JS/CSS는 1년 immutable, 원본 이미지·폰트는 1일 캐시 |

기존 로고·배경·공식 플랫폼 자산, 캘린더·하이라이트·등록 기능과 화면 문구를 유지했다. 등록 → 운영자 검토 흐름도 유지한다. 신규 제품 기능, DB 마이그레이션, 운영 배포는 추가하지 않았다.

## 2. 측정 결과

### 로컬 계산 및 메모리

Node.js 22.17 / React 18의 SSR 벤치마크로 공개 소개 309개를 사용했다. 브라우저 클릭 지연이나 LCP 측정과는 다르다.

| 항목 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 메인 캘린더 전체 렌더 | 1,548~1,575ms | 첫 렌더 72ms, 다음 렌더 19ms·16ms |
| 날짜 포맷터 생성 | 렌더당 약 12,418회 | 첫 렌더 4회, 다음 렌더 0회 |
| 개발 화면 초기 JS 합계 | 약 304KB | 약 207KB, gzip 약 69.5KB |
| 개발 화면 초기 CSS 합계 | 약 207KB | 약 153KB, gzip 약 26.3KB |

초기 용량은 HTML의 진입점과 정적 의존 모듈 합계이며 네트워크 캐시 전 기준이다. Vite에 남은 619KB 경고는 기존 운영 App 청크다. 개발 메인에서 이 청크를 다운로드하지 않는다.

20회 워밍업 후 강제 GC를 실행한 JS 힙은 13,818,136바이트, 추가 100회 렌더 후 GC 결과는 13,889,928바이트였다. 차이는 71,792바이트(약 70KiB)다. 이 검사는 반복 SSR 결과의 잔존 여부를 확인하는 보조 자료이며, 실제 브라우저 힙·이미지 디코딩 메모리·전체 경로의 누수 부재를 입증하지 않는다.

### 개발 도메인 HTTP

curl의 실제 HTTPS 요청으로 측정했다. 테스트 트래픽의 Cloudflare 진입 위치는 LAX였으며, 사용자의 국내 브라우저 조건과 다르다. 요청마다 DNS/TLS 및 다운로드 시간을 포함한다.

| 항목 | 결과 |
| --- | --- |
| 변경 전 통계 전체 응답 | 5.86초·6.43초, 응답 시작 대기 약 5.36~5.83초 |
| 최적화 후 통계 캐시 적중 | 전체 약 0.48~2.00초, 응답 시작 대기 약 0.47~0.72초 |
| 최종 배포 통계 강제 갱신 | 전체 3.894초, 응답 시작 대기 3.873초 |
| 최종 배포 소개 강제 갱신 / 적중 | 전체 1.206초 / 0.609초 |
| 자산 응답 | JS: `public, max-age=31536000, immutable`, 로고: `public, max-age=86400` |
| 비로그인 관리자 조회 | 401 / `Cache-Control: no-store`, 공개 캐시 표식 없음 |

중간 측정에서는 다운로드가 느려 강제 갱신 전체 시간이 9.318초까지 증가한 사례도 있었다. 캐시 적중과 첫 DB 집계를 구분해야 하며, 전체 로딩이 항상 0.5초라는 의미가 아니다.

## 3. 메모리 및 캐시 관리

- 날짜 포맷터만 모듈 단위로 최대 24개 저장하고 오래된 항목을 제거한다. 요청별 사용자 정보나 프로필은 이 캐시에 넣지 않는다.
- 소개 목록은 React 상태 한 곳에서 보관한다. 날짜 색인은 프로필을 복제하지 않고 참조하며, 조건 변경·화면 해제 시 이전 색인이 회수될 수 있게 한다.
- 비활성 화면에서는 전체 소개 요청을 보내지 않는다. 조회 중 화면 변경 시 AbortController로 중단한다. 문의 조회도 중단된 응답이 상태·저장소를 갱신하지 않게 했다.
- 기존 통계·등록 타이머와 이벤트 리스너의 해제 경로를 확인했다. 삭제된 화면의 전체 기록을 전역 Map에 누적하는 캐시는 만들지 않았다.
- 캐시는 공개 GET의 성공 응답만 대상으로 한다. 인증 요청, 비공개·no-store·Set-Cookie·오류 응답은 저장하지 않는다. 캐시 장애 시 원래 조회를 계속한다.
- 엣지 응답 헤더가 달라지는 사례를 확인해 만료 시각을 직접 검사한다. 적중 응답의 브라우저 유효 시간도 남은 시간으로 제한한다. 기존 브라우저의 긴 소개 캐시는 `version=2` 주소로 구분했다.
- 강제 새로고침은 캐시를 건너뛴다. 다른 방문자에게 공개 승인 결과가 반영되는 데는 소개 캐시 최대 30초가 걸릴 수 있다.
- 배포 직후 이전 화면이 삭제된 청크를 요청하면 1분에 한 번만 최신 HTML로 복구한다.

## 4. 검증 및 한계

- 프런트엔드 TypeScript·Vite 빌드, 백엔드 TypeScript: 성공.
- 회귀 검사 24개: 성공. 등록·관리자 승인·권한 거부, 일광 절약 시간, 통계 누락 구간·자정 경계·카테고리 필터·200개 이상 커서 연결, 공개 캐시 적중·만료·갱신·오류·비공개 격리를 포함한다.
- 실제 개발 UI: 달력 날짜 상세 → 소개, 등록 URL 자동 조회로 실제 활동명·소개 불러오기, 통계 25건 → 50건 연결, 모바일 주간·시간대 전환을 확인했다. 시험 등록이나 관리자 승인 데이터를 외부 DB에 만들지 않았다.
- 390px 모바일 설정에서 문서 폭과 표시 폭이 같아 가로 넘침이 없었다. 검증 후 시간대·보기·임시 뷰포트를 복원했다.
- 원본 브랜드 이미지 바이트를 변경하지 않았다. 최초 이미지 전송과 외부 웹 폰트 로딩은 네트워크 영향을 받으며, 이미지 캐시는 재방문에 효과가 있다.
- 캐시가 없는 새 조건의 통계는 원본 기록을 집계하므로 여전히 수초가 필요할 수 있다. 강제 중간 결과 저장 방식은 개발 DB 실측에서 약 2.70초 → 3.47초로 느려져 적용하지 않았다.
- Chrome DevTools MCP가 제공되지 않아 실제 브라우저 LCP·INP·CLS 및 힙 스냅샷은 측정하지 않았다. Lighthouse 점수나 브라우저 메모리 절감률을 추정해서 보고하지 않는다.
