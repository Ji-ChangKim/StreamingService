**최신 비교는 [27번 문서 10절의 카드·채팅 취향 발견 시뮬레이션](./27_CORE_FUN_DECISION_AND_SIMULATION.md#10-같은-사용자로-다시-비교--최신-의사결정)이다.** 카드 우선 권장은 보류하고 채팅 기반 방송 탐색의 수요를 먼저 확인한다. 아래 랜덤 팩·30종·8슬롯·23개 테이블·35~50인일과 비용 모델은 이전 가설이며 현행 착수 요구사항·견적이 아니다. 신규 기능 3개 동시 출시안도 승계하지 않는다. 인건비는 합산하지 않는다.

이전 안은 **기존 소개에서 버튜버를 알아보고, 무료 발견 팩으로 새 인물을 만나고, 저장한 카드와 관심 현황으로 돌아오는 4주 시험 서비스**를 제안했다. 카드 공급·로그인·지급·권한 철회·측정을 먼저 검증하고, 방송 수집 확대·예측·채팅·위키 자동화는 이후에 진행하는 가설이었다.

개발 작업량은 35~50인일을 권장 범위로 잡는다. 개발자 1명 전담과 25% 여유 기준으로 약 9~13주이며, 이후 4주 지표 관찰과 외부 모집·권한 확인의 대기 기간은 별도다. 검토안 작성은 실제 개발·운영 설정 변경·외부 연락·DB 반영을 포함하지 않는다.

## 2 1차 출시 포함 범위

| 묶음 | 제공하는 것 | 제외하는 것 |
| --- | --- | --- |
| 소개·탐색 | 기존 상세·대표 콘텐츠, 콘텐츠·언어 등 확보된 조건으로 찾기, 이유 표시 | 없는 음성·성격 데이터 생성, 고도 개인화 |
| 계정·관심 | 로그인 제공자 1종, 세션·탈퇴, 브라우저 관심의 선택 병합과 동기화 | 계정 간 합치기·다중 로그인 제공자·방송국 소유권 인증 |
| 무료 발견 | 4주·8슬롯·슬롯당 3장, 미보유·서로 다른 인물의 기본 카드 | 환영 추가 팩·1~2장 부분 지급·무제한 재추첨·포인트·거래 |
| 컬렉션 | 개인 보유 목록, 한 개의 최대 6장 공개 진열, 공개 해제·주소 복사 | 폴더·여러 진열장·드래그 편집·사용자별 PNG 생성·시장 |
| 관심 현황 | 기존에 공개된 다음 일정·대표 콘텐츠와 확인 시각 | 신규 실시간 수집 확대·읽지 않은 소식·푸시·메일·Discord 발송 |
| 운영 | 참여자·권한·카드·슬롯 등록, 지급 조회·중단·회수·삭제 작업 | 범용 CMS 재작성·팬 자유 게시판·본인 관리 화면 재도입 |
| 측정 | 소개·팩 성공·관심·공식 링크 이동·공유 유입·재방문 | 외부 실제 시청·구독·채팅 성향 증명 |

메인 하이라이트·캘린더·공통 Header·Footer는 보존한다. `/creator/:slug`, `/creators`, `/me/favorites` 본문에서 발견·컬렉션으로 연결한다. 기존 비로그인 열람과 관심 기능을 로그인 강제로 바꾸지 않는다. 신규 UI 문구는 기존 3개 언어로 제공하되 외부 자료의 자동 번역을 약속하지 않는다.

발견·카드 조회는 기존 승인 프로필과 검토된 미디어의 저장본·캐시를 읽는다. 팩이나 카드 한 장을 열 때마다 플랫폼 검색·외부 정보 동기화를 실행하지 않는다. 자료가 없거나 오래되면 확인 시각과 부족 상태를 표시하고 갱신은 운영 작업으로 분리한다. 실제 기존 상세 경로에서 외부 조회가 발생하는지는 S1에서 확인해 비용·성능 기준선에 포함한다.

### 2.1 카드와 슬롯 규칙

1. 첫 시험의 목표 공급은 권한이 확인된 30명·기본 카드 30종이다. 이는 확보 완료 수가 아니다.
2. 4주 8슬롯이며 월요일·목요일 00:00 KST 교체를 초기안으로 둔다. 슬롯의 UTC 시작·종료를 고정하고 새 가입자도 현재 슬롯에 1회 참여한다.
3. 한 이용자가 8번 모두 참여하면 최대 24장을 얻는다. 30종 대비 명목 여유는 6종이다. 철회·활동 중단·인물 오연결로 실제 여유는 줄어든다.
4. 팩은 취향 필터와 별개로 유효 미보유 풀에서 균등 추첨한다. 카드 등급·시청자 수·유료 여부를 가중치로 쓰지 않는다.
5. 유효 후보가 3명 미만이면 서버는 전체 보류한다. 원장·보유량·슬롯 소비가 발생하지 않는다. 미리보기는 지급 결과의 사전 확정이 아니다.
6. 발행된 슬롯의 풀은 수정하지 않는다. 철회된 카드는 제외하고 결과를 조작하지 않는다. 다음 슬롯에 필요한 새 풀은 새 버전으로 게시한다.
7. 슬롯 전 운영 점검에서 권한 철회 상태와 참여자별 미보유 후보 최소값을 확인한다. 부족하면 해당 슬롯을 열지 않고 안내한다. 새 카드 추가·주기 변경은 다음 캠페인 정책으로 정한다.

30종을 확보하지 못하면 권한 미확인 카드로 메우지 않는다. 기존 소개와 비로그인 발견 미리보기의 사용성 검증까지만 진행하고, 실제 지급 시험 일정은 공급에 맞춰 조정한다.

## 3 개발 순서와 공수

| 순서 | 작업 | 선행 판단과 결과물 | 인일 |
| --- | --- | --- | ---: |
| S1 | 범위·환경·측정 기준 확정 | 개발 DB 분리안, 30명 확보 계획, 권한 범위·데이터 기준·화면 초안 | 5~7 |
| S2 | 회원·세션·관심·탈퇴 | 로그인 제공자 검증, 복구·삭제·관심 병합·접근 권한 | 6~9 |
| S3 | 참여자 대응·자산·운영 등록 | 기존 프로필 대응과 변경 확인, 라이선스·카드·슬롯·중단 도구 | 5~7 |
| S4 | 지급 엔진과 선행 검증 | 동시 요청·응답 유실·후보 부족·철회·0행 실패를 원자적으로 처리 | 6~9 |
| S5 | 발견·개봉·컬렉션·링크 공유 | 지연 로딩·공개 해제·고정 OG·기본 접근성 | 5~8 |
| S6 | 관심 현황·제품 계측 | 현재 공개 정보 연결, 분모가 분명한 발견·방송 이동·재방문 집계 | 4~5 |
| S7 | 통합·회귀·운영 인수·제한 공개 | 기존 화면 보존, 두 기기·모바일·삭제·복구·사용량 확인 | 4~5 |
| **합계** | **R0~R1** | **외부 승인 대기·시험 4주 관찰은 별도** | **35~50** |

S1 후 콘텐츠 권한 확보는 개발과 병행할 수 있으나 작업량과 달력 대기를 구분한다. S4는 S3의 일부 카드로 검증하고 성공 전 개봉 UI를 크게 확장하지 않는다. 지급이 중단되더라도 기존 소개·관심 목록과 이미 확정된 카드 조회는 유지한다.

기본 카드 30종을 하나의 공용 템플릿과 제공된 허용 자산으로 편집하는 작업을 S3에 포함한다. 새 일러스트·음성 제작·외부 계약 협상은 포함하지 않는다. 1인일 8시간, 주 5일 전담 기준 순수 7~10주이며, 25% 여유는 약 44~63인일·9~13주다. 동시 작업 인원을 늘린다고 이 기간이 그대로 나뉘지는 않는다.

## 4 최소 DB와 운영 설계

R1은 기존 catalog를 읽는 어댑터와 별도 `engagement_db`를 사용한다. 참여 30명에 대해서만 `creator_links` 대응표를 만들고, 전 버튜버의 정규화·스키마 이관·새 analytics DB는 R2 이후로 둔다.

| 영역 | R1 테이블 |
| --- | --- |
| 계정·관심 | users, auth_identities, user_sessions, follows |
| 참여자·권한 | creator_links, asset_licenses, card_editions |
| 발행·지급 | campaigns, campaign_pool_versions, campaign_pool_items, pack_slots, pack_openings, pack_draws, card_ledger, inventory_items |
| 공개 진열 | collections, collection_items |
| 운영·측정 | outbox_jobs, processed_jobs, audit_events, product_events, product_daily_metrics, deletion_jobs |

총 23개 테이블을 후보로 두되 실제 DDL 확정 전 중복·공통 메타데이터를 다시 검토한다. 이름이 여러 개라는 이유로 모두 별도 서비스나 별도 DB로 만들지 않는다. 정규화가 필요한 지급 행은 유지하고, R1에서 쓰지 않는 위키·예측·알림 테이블은 만들지 않는다.

R1의 `creator_id`는 `creator_links.id`를 참조하고 향후 catalog 정규 ID로 승계한다. 기존 slug·채널·프로필 원본은 변경하지 않는다. 개봉·draw·원장·보유량·권한 확인은 같은 engagement DB에서 처리한다. 지급 결과 확인은 캐시나 지연된 읽기 복제본에 의존하지 않는다.

outbox는 초기에 예약 작업이 짧게 조회·처리한다. 별도 Queues·Durable Objects·상시 수집기는 R1 필수 구성에서 제외한다. 작업 재실행은 유일 키로 방지하고, 비어 있는 작업 큐를 확인할 때마다 DB에 heartbeat를 쓰지 않는다.

### 4.1 누락했던 실패 처리

- 삭제·공개 해제는 동기적으로 접근을 막고 후속 작업으로 파일·캐시·다른 집계를 정리한다. 삭제 작업의 단계·오류·재시도·완료 시각을 남긴다.
- 카드 원본·증빙은 비공개 보관을 기본으로 한다. 공개 이미지는 통제된 경로로 제공하고 내부 캐시 TTL은 최대 60초를 목표로 검증한다. 외부에 이미 저장된 이미지나 캡처를 회수한다고 약속하지 않는다.
- 이미 지급된 카드의 권한이 철회되면 원장을 보존하되 이미지는 대체한다. 그 기록을 별개의 새 카드로 조용히 바꾸지 않는다.
- 로그인 문제는 해당 제공자의 재인증과 지원 절차로 처리한다. 이메일만 같다는 이유로 다른 계정·소유 목록을 합치지 않는다.
- R1의 공개 진열은 실제 소유·공개 가능 카드 6장 이하만 허용하고 자유 텍스트·사용자 이미지 업로드는 제외한다.
- 가입·열람·측정에 필요한 정책 문구와 연령·동의 적용 범위를 출시 전에 확정한다. 외부 영상·로그인·측정 쿠키의 도입 방식도 함께 확인한다.

## 5 4주 시험과 출시 기준

### 5.1 기술 출시 기준

| 항목 | 필수 확인 |
| --- | --- |
| 콘텐츠 | 사용권·공식 채널·대표 콘텐츠·참여자 대응 검토, 8슬롯 공급 계획 |
| 지급 | 동일 슬롯 동시 20요청·응답 유실·권한 철회·후보 2명에서 중복·부분 지급 없음 |
| 정보 | 일정 미정·변경·삭제와 자료 부족을 실제 상태대로 표시 |
| 개인정보 | 다른 계정 접근 차단, 탈퇴·공개 해제·세션 폐기·후속 삭제 확인 |
| 성능 | 기존 메인과 복귀 화면 보존, 신규 화면·이미지의 실제 모바일 측정 |
| 복구 | 원장 대조·백업 복구·중단 버튼·실패한 후속 작업 재시도 |
| 비용 | 일주일 사용량에서 계정 전체 기준의 월 추정과 예산 경보 확인 |

처음에는 초대 100~300명에게 제한 공개한다. 무제한 공개 전 사용량과 오류를 확인한다. 신규 카드·지급에 문제가 생기면 해당 기능만 중단하고 서비스 전체와 운영 DB를 이전 상태로 무조건 되돌리지 않는다.

열람은 계속 공개하고 실제 팩 지급은 시험 참여가 활성화된 계정으로 제한한다. 계정별 제한과 요청 제한을 함께 사용하며 IP·기기 정보만으로 동일인 여부를 확정하지 않는다. 다중 계정 의심 요청·관리자·시험 계정을 일반 성과에서 제외할 수 있게 한다.

### 5.2 제품 지표의 분모

| 지표 | 분모와 해석 |
| --- | --- |
| 팩→관측 범위 내 첫 소개 | 성공 개봉 계정 중 24시간 안에 계정 생성·측정 동의 이후 시험기간에 처음으로 해당 인물 소개를 연 계정. 관측 시작일을 함께 기록 |
| 소개→공식 링크 이동 | 새 소개 확인 계정 중 24시간 안에 해당 공식 링크를 누른 계정. 실제 시청률 아님 |
| 비로그인 소개 유입 | 동의한 범위에서 확인 가능한 방문 단위. 로그인 계정의 발견률과 혼합하지 않음 |
| D7 | 첫 유효 방문일 기준 7일째 재방문. 아직 7일이 지나지 않은 이용자는 분모에서 제외 |
| W1 | 첫 방문 다음 날부터 7일째까지 재방문. D7과 별도 표기 |
| 공급과 편중 | 계정별 남은 유효 후보·슬롯 보류 수, 인물별 노출·클릭 수. 지급량만 비교하지 않음 |

30%·10%·D7 20%는 방향 검토용 초기 가설로 유지하되, 인원수를 반드시 병기한다. 예를 들어 100명이 팩을 열고 30명이 새 소개를 보며 그중 3명이 공식 링크를 누르면 단계별 30%·10%지만 최종은 3명이다. 이를 팬 3명 증가로 표현하지 않는다.

R1의 첫 소개는 VDébut에서 관측한 범위의 첫 조회이며 실제로 처음 알게 된 버튜버라는 뜻이 아니다. 신규 계정은 30일 과거 이력이 없으므로 30일 무조회 지표를 적용하지 않는다. 충분한 이력이 쌓인 뒤 별도 지표로 추가하고 실제 새 발견 여부는 인터뷰로 보완한다. 크리에이터가 데려온 팬과 내부 탐색 유입을 출발 영역·공유 식별자로 구분하고 OG 미리보기 수집기는 유효 방문에서 제외한다.

시험은 A/B 유의성 검증으로 설계하지 않는다. 유효 개봉 계정이 100명 미만이면 비율만으로 성공·실패를 확정하지 않고 동선 오류와 5~10명 인터뷰를 우선한다. 4주 종료 후 새 발견·공식 이동이 없으면 보상량을 늘리기보다 소개·후보·유입 동선을 수정한다. 표본이 부족하다고 미보유 후보가 소진된 캠페인을 같은 조건으로 무기한 연장하지 않는다.

## 6 1차 출시의 추가 인프라 비용

기존 방송 통계 운영비와 새 카드 기능의 추가 사용량을 구분한다. 아래는 30일 동안 가입한 N명과 하루 활성 D명에 대한 보수적 활동 예산이다. 4주 캠페인 8슬롯을 모두 참여한다고 계산하며, 신규 방송·채팅 수집은 0이다.

### 6.1 사용량 산식

```text
P = N × 8                         # 성공 팩 수의 상한
E = D × 30 × 10                  # 제품 이벤트
R = D × 30 × 40 × 0.25 × 50
  + P × 100 + E
  + N × 30 × 8 + 100,000         # 슬롯 전 30종 보유 검사·운영 예약
W = N × 12 + D × 30 × 24
  + P × 80 + E × 4 + 20,000      # 인덱스·삭제·운영 쓰기 예약
G = 0.02 + N × 5,000 / 1e9
  + P × 3 × 1,000 / 1e9
  + E × 500 / 1e9                # 새 DB의 30일 점유 GB 추정
Q = D × 30 × 40 + 43,200         # 요청과 예약 호출의 보수적 예산
CPU = Q × 5 + P × 20             # CPU ms 가정
R2_GET = D × 30 × 20             # 실제 객체 GET 예산
```

R1의 P당 80행은 실측 전 상한 가정이다. 40요청·DB 비율·행 수·CPU·자산 GET은 실제 운영값이 아니며 원장·인덱스·로그 크기로 교체한다. 43,200회는 분당 예약 실행을 모두 요청 예산에도 포함한 보수적 값이며 Cron 실행이 동일한 인바운드 요청으로 과금된다는 설명이 아니다. 유휴 작업 조회의 CPU를 0으로 간주하지 않는다.

### 6.2 규모별 계산

| 입력과 결과 | 초대 시험 | 다음 단계 비교 | 상한 비교 |
| --- | ---: | ---: | ---: |
| 신규 가입 N | 300 | 1,000 | 5,000 |
| 하루 활성 D | 100 | 300 | 1,000 |
| 최대 팩 P | 2,400 | 8,000 | 40,000 |
| 월 읽기 R | 1,942,000 | 5,730,000 | 20,600,000 |
| 월 쓰기 W | 407,600 | 1,248,000 | 5,200,000 |
| 신규 DB 점유 G | 0.0437GB | 0.0940GB | 0.3150GB |
| 요청 예산 Q | 163,200 | 403,200 | 1,243,200 |
| CPU 예산 | 864,000ms | 2,176,000ms | 7,016,000ms |
| R2 GET 예산 | 60,000 | 180,000 | 600,000 |

R2 Standard는 이미지·증빙·고정 OG 합계 0.25GB, 월 Class A 작업 10,000회 이하를 가정한다. 계정의 해당 포함량이 남아 있으면 세 시나리오의 Workers·D1·R2 초과 사용 요금은 0으로 계산된다. Paid 신규 가입이 필요한 계정의 기본료는 월 $5다. 이미 Paid이면 신규 DB를 만든다는 이유로 $5를 다시 더하지 않는다. 이는 모든 기존 서비스 비용이 $5라는 뜻이 아니다. [Workers 요금](https://developers.cloudflare.com/workers/platform/pricing/), [D1 요금](https://developers.cloudflare.com/d1/platform/pricing/), [R2 요금](https://developers.cloudflare.com/r2/pricing/)

실제 추가 청구는 `계정 기존 사용량 + 신규 사용량의 요금 - 기존 사용량의 요금`으로 계산한다. 현재 청구액·포함량 잔여분은 아직 확인하지 않았다. 기존 KV·방송 수집·도메인·세금·외부 계약은 이 추가 모델 밖에 둔다.

### 6.3 실제 지출 기준과 현행 비용표

| 항목 | 현금 지출 기준 | 전제 |

현행 단일 핵심의 사용량·DB 읽기·쓰기·저장량과 후보별 실제 지출 비교는 [27번 문서 7절](./27_CORE_FUN_DECISION_AND_SIMULATION.md#7-추가-비용-비교--인건비-제외)을 따른다. 이전 월 $20~50은 필수 청구가 아닌 관리 예비비였으므로 출시 비용 전망에서 제거한다. 현재 계정의 청구액을 확인한 것은 아니다.

## 7 책임과 범위 변경 기준

| 책임 | 해야 할 일 | 부재 시 |
| --- | --- | --- |
| 제품 담당 | 범위·성공 기준·인터뷰·다음 단계 판단 | 개발 착수 일정 확정 보류 |
| 개발 담당 | 지급·계정·관심·모니터링·복구 | 신규 발행·지급 확대 중단 |
| 콘텐츠·권한 담당 | 30명 대응·허락·크레딧·소식·철회 | 신규 슬롯 공개 보류 |
| 운영 대체 담당 | 오류·삭제·권한 철회 확인과 중단 | 대응 가능한 범위로 시험 제한 |

같은 사람이 여러 역할을 맡을 수 있지만 개발 전담 시간과 운영 시간을 중복 계산하지 않는다. 권한·로그인·지급 검증이 예상 공수 상한을 넘으면 컬렉션 편집이나 홍보물 제작을 추가하지 않고 범위를 다시 잡는다. 데이터 부족·표본 부족·외부 승인 대기는 개발 완료율로 숨기지 않는다.

이 안의 출시 판단은 검토 기준이다. 서비스 구현·DB 생성·운영 데이터 변경·외부 연락·배포는 이번 문서 보완에서 수행하지 않는다.
