## 1 공정의 결론과 첫 적용 범위

**검색·후보 저장·정보 정리·자동 검사·승인 후 반영·재확인은 자동화하고, 초기 최종 승인은 운영자가 한다.** 후보 DB와 공개 데이터는 같은 기존 DB 안에서 논리적으로 구분한다. 검색 결과가 저장됐다는 이유로 화면에 노출하지 않는다.

첫 연결 대상은 기존 코드가 있는 X의 치지직 데뷔 공지 검색이다. 검색/API 접근·사용 범위·쿼터·비용과 실제 성공 여부는 아직 미확인이다. 허용 연결을 확보하기 전에는 비활성으로 두고 자동 운영 중이라고 표시하지 않는다. 다음 연결은 허용된 웹 검색, 발견한 공식 채널의 커뮤니티, SOOP 공식 일정 순으로 범위를 정한다. 어느 것도 아직 구현/운영이 완료됐다는 뜻이 아니다.

공지에서 반드시 관리할 정보는 **어디서 조사했는가 / 누가 / 언제 / 어디서 데뷔하는가**다. 채널 전체 조회나 인기순 목록 확장을 주력 수집 경로로 삼지 않는다. 첫 출시에서 자동 승인은 제외하며, 안정화 후 출처·항목별로 별도 결정한다.

## 2 단계별 입력·자동 처리·완료 결과

| 단계 | 입력 | 자동으로 할 일 | 결과·다음 조건 |
| --- | --- | --- | --- |
| 0 출처 설정 | 검색어·소스·허용 항목·실행 주기·예산 | 설정된 출처만 실행 대상으로 선택 | 연결 미확인/중지 소스는 미실행 상태로 표시 |
| 1 검색·수집 | 활성 출처·직전 성공 시점·커서 | 새 공지와 변경 공지 조회, 원문 식별자·작성자·발행/확인일·근거 참조 확보 | 성공/실패/부분 수집과 사용량을 기록 |
| 2 후보 저장 | 원문 항목·채널 주소 | 원문 키·주소 정규화, 기존 후보·공개·대기·차단 대조 | 새 후보 또는 기존 후보/행사의 변경 제안. 화면 미노출 |
| 3 정보 정리·보강 | 공지·공식 연결·후보 | 활동명·일정·플랫폼·채널 추출, 기존 채널 조회로 제공 정보 보강 | 각 값에 근거 연결. 없는 값은 미확인 |
| 4 자동 검사 | 후보 버전·추출 값·기존 데이터 | 누락·형식·주소·중복·시간대·행사 종류·충돌·공개 기준 검사 | 검수 가능 / 재확인 필요 / 보류 사유 생성 |
| 5 운영자 검수 | 원문·추출 정보·자동 검사·변경 전후 | 비교 화면과 공개 예정 미리보기 제공 | 운영자가 수정 후 승인·보류·반려. 승인 값·버전 고정 |
| 6 공개 반영 | 승인된 변경 계획·대상 버전 | 승인 유효성 재확인, 공개 데이터·이력 저장, 공개 반영 작업 생성 | 반영 성공/실패를 승인 상태와 별도로 관리 |
| 7 화면 확인·유지 | 반영 결과·공개 API·캐시·원문 | 관련 캐시 갱신·공개 데이터 확인, 이후 변경 재확인 | 공개 완료 또는 노출 확인 실패. 변경은 새 검수 제안 |

정상 흐름은 **수집 → 후보 저장 → 정리/검사 → 검수 대기 → 승인 → 반영 대기 → 공개 완료**다. 보류·반려·반영 실패는 별도 상태이며 검수 대기와 섞지 않는다.

## 3 어디서 어떻게 검색할 것인가

| 경로 | 조회 계획 | 확보 값·한계 |
| --- | --- | --- |

| 공식 채널 커뮤니티 | 앞 단계에서 발견한 공식 채널/게시물 주소 | 일정·수정·취소 원문. 전체 커뮤니티 일괄 조회 기능이 있다고 가정하지 않음 |
| SOOP 공식 일정·지정 공지 | 허용된 목록/피드의 이전 결과와 비교 | 사람·행사·일정·채널. 이용 조건·구조 확인 후 별도 활성화 |

검색어는 처음에 사람이 정하고, 반복 조회·게시물 비교·주소 추출은 시스템이 한다. 연결되지 않은 검색 원천을 운영자가 매번 대신 검색해야만 돌아가는 상태라면 그 원천은 수동 조사로 표시하며 자동화 성과에 포함하지 않는다.

첫 수집은 허용된 조회 기간을 기준 자료로 확보하고 관측 시작점을 기록한다. 이후 직전 성공 시점과 겹치는 기간을 조회해 늦게 노출된 공지를 잡되 원문 키로 중복 제거한다. 페이지 잘림·쿼터 중단은 미완료로 기록하고 커서/작업을 이어 간다. 조회 구간이 끝까지 완료된 경우에만 구간 성공 기준점을 전진시키고, 부분 수집은 재개 커서와 미완료 범위를 별도로 보존한다. 제공자의 과거 조회 기간 밖 공백은 자동 복구됐다고 표시하지 않는다.

## 4 실행 주기와 작업 상한

모두 초기 설정 제안이며 실제 권한·소스 지연·적중량에 맞춰 조정한다.

| 작업 | 초기 제안 | 과부하·미처리 대응 |
| --- | --- | --- |
| X 신규/변경 검색 | 매일 09:00·15:00·21:00 KST, 검색 묶음 2개·각 최대 2페이지 | 조기 종료 가능. 잘림이면 부분 수집·다음 작업 기록. 모든 신인 포착을 보장하지 않음 |
| 후보 상세 보강 | 수집 후 이어서, 1회 최대 20건 | 남은 후보는 다음 배치. 순서·대기 시간 표시 |
| 근거 부족 후보 재확인 | 하루 1회, 최대 3회·7일 범위 초기안 | 이후 보류·만료 대상으로 전환. 사람이 모두 조사해야 하는 의무를 만들지 않음 |
| 활성 일정 변경 확인 | 지원되는 원문/공지에서 하루 1회 | 임박·변경 단서 우선. 원문 재조회만으로 다른 새 공지를 모두 찾는다고 가정하지 않음 |
| 운영자 검수 | 하루 1회 묶음 검토 초기안 | 임박 일정·취소/중요 변경 우선. 단순 무변화 건은 목록에서 제외 |
| 승인 후 반영·캐시 확인 | 승인 시 반영 작업 생성, 실패 시 제한 재처리 | 승인만 완료·공개 미완료인 상태를 구분. 무한 재시도 금지 |

X 기본 검색은 2묶음×2페이지×하루 3회×30일=월 최대 360요청 가정이다. 검색 재시도는 별도 하루 최대 2요청을 예약하면 월 60요청, 합계 최대 420요청이다. **접근/페이지 지원을 확인한 요금 견적이 아니며** 후보 보강·본문·일정 재확인·다른 검색 소스 요청은 여기에 포함되지 않는다. 게시물당 과금 등 실제 단위도 확인해야 한다.

동일 작업의 중복 실행을 잠금으로 막고 소스별 호출 상한·동시 처리·다음 실행 시간을 관리한다. 기존 예약 작업과 새 수집기가 같은 원천을 이중 조회하지 않도록 실행 소유자를 하나로 정한다. 실행기·내부 작업·외부 HTTP 요청 수는 별도로 집계한다.

## 5 DB에 무엇을 나눠 저장할 것인가

아래는 논리 영역이며 실제 테이블 신설/필드 변경은 아직 하지 않았다.

| 논리 영역 | 필요한 값 | 역할 |
| --- | --- | --- |
| 출처 설정·실행 | sourceId, query, mode, lastSuccessAt, cursor, status, counters, nextRunAt | 현재 어떤 출처가 동작하고 어디까지 읽었는지 추적 |
| 원문·근거 | sourceItemKey, sourceUrl, authorRef, publishedAt, observedAt, contentHash, 최소 근거 | 같은 공지 재수집·원문 수정·출처 추적. 불필요한 원문/이미지 전체 저장 제외 |
| 후보·변경 제안 | candidateId, version, channelKey, eventRef, origin, proposedValues, missing/conflicts, reviewState | 공개 전 신규/정정 정보. 인물·행사·원문 관계 보존 |
| 검수·승인 기록 | candidateId/version, 승인할 값의 해시, 대상 기존 버전, reviewer, decision, reason, approvedAt | 누가 어떤 내용을 승인했는지 고정. 변경 시 과거 승인 이력은 보존하되 새 버전에 사용 금지 |
| 반영 작업·이력 | operationId, approvalRef, status, attempts, diff, before/after, error, appliedAt | 재실행 중복 방지·실패 재처리·복구 |
| 공개 데이터 | 기존 프로필·미디어·일정/행사·공개 상태 | 검수된 자료만 공개 API에 제공. 후보를 화면 조회에 혼입하지 않음 |

기존 `portal_requests`는 사용자 접수와 PENDING/APPROVED/REJECTED 상태가 있다. 수집 후보의 보류/재확인/반영 실패를 그 상태값에 억지로 넣지 않는다. 기존 관리자 인증·정정·이력을 재사용하되 후보 목록/검수와 반영 상태를 연결하는 기능은 별도 개발한다. 기계 수집을 가짜 사용자 접수 키로 위장하지 않는다.

채널은 플랫폼 고유 ID로 식별하고 이름만으로 합치지 않는다. 같은 채널의 다른 행사는 분리하며 날짜가 바뀌었다는 이유만으로 새 인물·행사를 만들지 않는다. 기존 공개 주소와 수동 확정/잠금 값을 보존한다. CSV 후보 저장/검증을 실제 반영 또는 정본 T 상태로 해석하지 않는다.

## 6 자동 검사와 운영자 검수의 경계

| 자동으로 확인 | 운영자가 확인 |
| --- | --- |
| 주소 형식·지원 플랫폼·고유 채널 ID·기존 등록/대기/차단 중복 | 공지 작성자가 본인/공식인지와 채널 관계의 모호한 사례 |
| 이름·일정·시간대·방송 주소의 유무, 날짜/요일/시각 충돌 | 신규 인물/재데뷔/이적·부계정, 상충한 근거의 최종 선택 |
| 공지 발행일과 예정일 분리, 변경 문구·중복 원문·행사 후보 구분 | 대표 자료·주요 사실 변경·공개 적합성 및 최종 승인 |
| 기존 공개 기준에 따른 차단 신호·제공 필드·승인 버전 유효성 | 삭제/권리 요청·소스 규칙 변경·오류 표본 |

정보 추출은 명시된 텍스트·정형 자료부터 한다. 날짜가 이미지에만 있거나 연도·시간대·동일 인물이 모호하면 추측하지 않고 보류한다. OCR/AI는 초기 필수 계약이 아니며 도입해도 추출 결과가 공식 사실의 증명이 되지는 않는다. '내일' 등 상대 날짜는 공지 발행 시각/시간대 근거가 명확할 때만 해석한다.

검수 화면에는 **원문 열기 / 추출한 4항목 / 근거·자동 검사 사유 / 기존 값과 변경값 / 공개 예정 미리보기 / 승인·보류·반려**를 제공한다. 편집하면 후보 버전을 올린 후 그 버전을 승인한다. 사람 이름·날짜를 다시 타이핑하는 대신 자동 추출값의 수정·선택에 집중한다.

일정이 미정이어도 인물 소개의 최소 조건을 갖추면 **인물 소개만 승인**할 수 있다. 행사/캘린더 노출은 별도 승인 범위로 정하고 정확한 지원 일정만 연결한다. 초기에는 자동 검사 통과를 자동 최종 승인으로 취급하지 않는다.

## 7 승인 후 실제 공개되는 조건

1. 관리자 인증과 승인 권한을 확인하고 승인 대상 값·후보 버전·근거·변경 전 상태를 고정한다.
2. 반영 직전에 후보/공개 데이터 버전과 차단 상태를 다시 비교한다. 후보 수정·수동 정정·철회 등 충돌이 있으면 재검수로 보낸다.
3. 작업 식별자로 중복 실행을 막고 프로필/일정·채택 근거·이력·반영 작업을 가능한 원자적 단위로 기록한다. 외부 API를 DB 반영 중 호출하지 않는다.
4. DB 반영이 성공하면 관련 캐시를 갱신하고 공개 조회에서 승인한 데이터/버전이 반환되는지 확인한다. 캐시 갱신 재처리는 저장된 작업으로 이어 간다.
5. 후보는 공개 완료로 표시하고 결과 주소를 제공한다. DB 반영/캐시 확인이 실패하면 반영 실패 또는 노출 확인 실패로 남긴다. 승인됐다는 사실만으로 공개 완료라고 표시하지 않는다.

**승인된 버전과 공개된 버전이 같아야 한다.** 승인 후 후보가 수정되면 새 검수가 필요하다. 기존 승인의 감사 이력을 지우지 않고 유효한 승인 대상만 바꾼다. 새 원문 수정은 현재 공개 정보를 직접 덮어쓰지 않고 새 변경 제안으로 만든다.

## 8 실패·중복·삭제 처리

| 상황 | 자동 대응 | 직접 판단 |
| --- | --- | --- |
| 검색 오류·타임아웃·할당량 | 실패/다음 재시도 기록. 성공 시점 임의 갱신 금지 | 지속 실패 소스·규칙 조정 |
| 인증/접근 거부 | 해당 소스 중지, 기존 공개 데이터 유지 | 접근 설정·이용 범위 확인. 우회 수집하지 않음 |
| 페이지/일일 한도 도달 | 부분 수집·남은 작업/공백 기록 | 장기 적체 시 범위·주기 조정 |
| 같은 공지·같은 채널 반복 | 원문 지문·채널 키로 비교, 무변화 재등록 금지 | 동일 인물 관계가 불명확할 때만 검토 |
| 근거 부족 | 제한 재확인 후 보류·만료 | 필요한 경우 선택적 보완. 모든 건을 강제 배정하지 않음 |
| 승인 후 데이터 충돌 | 반영 중지·재검수 | 변경값·잠금·승인 범위 재판단 |
| DB 반영/캐시 갱신 실패 | 같은 작업 ID로 제한 재처리, 완료 상태 분리 | 반복 실패 원인 확인·복구 |
| 일정 변경/취소·원문 삭제/철회 | 변경 제안·영향 필드·차단 상태 연결 | 중요한 정정·삭제·긴급 공개 중지 판단 |

조회 실패 한 번을 삭제·취소로 판단하지 않는다. 철회/삭제가 확정된 항목은 재수집으로 다시 공개되지 않게 최소 차단 기록을 유지한다. 로그·미해결 후보 보관 기간은 공개 목적·소스 조건에 맞춰 확정하며 연락처·토큰·원문 전체를 오류 로그에 남기지 않는다.

## 9 개발 순서와 산출물

| 순서 | 만들 것 | 완료 기준 |
| --- | --- | --- |
| A 공정/출처 계약 | 검색·필드·허용 범위·주기·상태·비용 입력 | 4항목의 출처와 자동/직접 경계가 명확. 미연결 소스 구분 |
| B 후보 DB·검수 화면 | 원문/후보·중복·추출/검사·버전·비교·미리보기 | 고정 예시로 후보 저장→검수. 공개 데이터 미변경 |
| C 승인·반영·복구 | 승인값 고정·상태 비교·반영 작업·공개 조회/캐시 확인 | 승인 버전만 노출. 중복·실패·동시 수정에서 안전 |
| D 첫 검색 연결·정기 실행 | X 기존 조사 연결 재사용·상한·커서·실패 상태 | 외부 실행이 허용된 단계에서 실제 새 공지 후보까지 확인. 키/권한 미확인은 미동작으로 표시 |
| E 화면 연결·지속 운영 | 도감·상세·기존 관심 기본 정보, 변경 재확인·예외 요약 | 새 공지→공개→일정 변경까지 같은 기록으로 반복 |

출처의 이용 가능성·필드 계약을 A에서 확인한 뒤 B/C를 준비하고 D에서 실제 연결을 통합한다. 개발 중에는 고정 예시로 승인/반영 흐름을 먼저 확인할 수 있지만 그것을 실제 자동 발굴 성공으로 보고하지 않는다. 이 문서 작성 시 A~E의 구현·실호출·DB 반영은 모두 미착수다.

## 10 운영 성과·비용·완료 기준

관리자 요약에는 소스별 마지막 성공·실패/부분 수집, 새 공지·중복·4항목 확보·검수 대기/보류, 승인 후 미반영·공개 완료, 대기 시간·직접 검수 시간, 호출/게시물·DB·CPU·실제 비용을 표시한다. 새 공지 없음과 미실행/실패를 구분한다.

인건비는 제외한다. 기존 Worker·D1·관리자/조회/이력을 우선 재사용하고 별도 상시 서버·메시지 서비스·외부 AI를 필수 도입하지 않는다. 월 실비는 **기존 기본료+필요 플랜 차액+공유 잔여량 초과료+실제 검색/API/로그·백업 요금**으로 산정한다. X 검색 최대 420회 가정은 전체 수집량이나 월 요금이 아니다. 이전 월 1만원/3만원과 인기 목록 수집량을 견적으로 재사용하지 않는다.

첫 완료 기준은 이름을 몰랐던 인물의 공지에서 4항목을 확보하고, 후보 저장→검수→승인→공개 확인→이후 변경 제안까지 반복되는 것이다. 검색 오류, 이미지에만 있는 날짜, 중복 공지, 재데뷔, 일정 미정, 승인 후 수정, 중간 반영 실패·재실행·캐시 지연도 확인한다. 등록 숫자만으로 성공을 평가하지 않는다.

메인 하이라이트·실제 캘린더·PortalStage·Header/Footer는 유지한다. 정확한 지원 일정만 기존 캘린더로 연결한다. 신규 회원/소유권 관리 화면·추천 게임·채팅 분석은 이번 공정에 추가하지 않는다.
